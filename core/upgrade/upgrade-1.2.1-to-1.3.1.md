# 1.2.1 → 1.3.1 升级说明

> 状态：正式发布升级契约。只有官方固定 `v1.3.1` 标签、对应 Release 对象、清单和解压树全部一致，且用户明确同意本次实例升级时，本文才允许进入隔离迁移；它不授权任何新的提交、推送、标签、Release 或 Pages 动作。

1.3.1 保留 1.3.0 的严格启动胶囊、正式结果证据索引以及“候选学习”和“正式资产授权”分离，并修复 1.3.0 发布清单仍标为本地候选、宽泛规则误伤空结构占位的问题。它也把“用户已经说记住”统一为一次聚焦的精确预览确认。普通启动仍只读取极小入口；只有升级、成熟度核对或真实任务命中时才展开相应正文。

## 升级前必须知道的变化

- `instance/startup-capsule.toml` 是从严格实例清单在模型上下文外生成的派生入口。它不是第二份用户档案，也不能接收自由文字。
- `instance/validations/index.toml` 是能力、SOP 和宿主执行经验成熟度的低敏证据索引。普通启动不加载它；只有成熟度核对、资产维护、升级或快照重建才按需读取。
- Asset Schema 升到 1.3。`risk-tiered` 只决定主动观察、候选验证和复核的先后顺序，不再能授权任何正式资产。
- 每项正式记忆、能力、SOP 和经验都必须来自用户当前明确确认，或能够独立核验的旧有明确批准。模型判断“风险低”、重复成功或旧策略字段都不能替代用户确认。
- 正式资产与直接路线都要登记相同的 `confirmation` 门。这个门说明以后执行真实动作前何时还要询问用户，不表示用户已经批准资产。

## 必须采用隔离副本

先对 1.2.1 实例建立完整、可回滚的隔离副本，再执行迁移。升级器必须保留原实例、用户档案、正式资产、信号、宿主档案、治理排期、验证记录、登记过的专业扩展和本地私密层；不能直接把 1.3.1 空白模板覆盖到已实例化助手。

目标 1.3.1 内容必须来自官方固定标签和 Release。`maintainer-private/`、`workspace/`、Git 元数据、依赖、缓存和临时构建内容都不能进入目标；`.assistant-local/` 与 `.assistant-private/` 仍按宽泛规则禁止，唯一例外是发布清单逐字列出的九个普通零字节 `.gitkeep`。目录记录只是 ZIP 容器元数据；任一占位含正文、是链接、路径不在精确清单中，或调用方自行追加例外，都立即停止。

## 迁移顺序

### 1. 先迁移严格实例清单

校验实例 ID、方向锁、交流方式、学习偏好和用户档案引用。旧学习策略若缺字段或曾暗示“低风险自动正式化”，保留兼容的候选观察偏好，但把正式激活固定为用户明确确认；语义不明时采用 `manual-only`，不能猜。

### 2. 保守补齐确认门

只读取需要迁移的资产 frontmatter 和与它一一对应的地图路线，不扫描全部正文：

- 旧资产是低风险且缺 `confirmation`：兼容值为 `none`；
- 中风险、高风险或风险不明：兼容值为 `risk-dependent-before-action`；
- 已有一个更严格且在正式注册表中的门：保留，不得降级；
- 未知门、路线与正文对不上、目标或身份不明：该资产进入 `review`，不读正文，不猜值。

地图和 frontmatter 必须在一个事务中同时修改、重新解析并逐字核对一致。`confirmation` 不是批准记录，补字段不能把资产变成“已获授权”。

### 3. 复核旧正式授权

1.2.1 中如果存在 `policy-authorized` 或其他由策略推导的正式资产：

- 只有旧记录中能够独立核验真实用户明确批准时，才迁移为 `approval_state=explicit` 与 `activation_basis=existing-approved-migration`；
- 找不到真实批准，资产和路线都进入 `review`，等待用户用普通语言确认；
- 不得把低风险、使用次数、模型判断、旧字段或升级行为本身写成批准证据。

这个复核只改变资产是否可以进入普通召回，不删除正文。升级预览要把等待确认的资产用用户能看懂的名称列出。

### 4. 建立验证证据索引

若索引不存在，先创建一个与当前实例 ID 绑定的空索引。然后只根据已经存在的真实验证记录和资产 `validation_refs` 建立闭包：

- 不从文件时间推算验证时间；
- 不把模型自称成功、测试夹具、一次修复中的反复尝试当作多项独立真实任务；
- 不读取秘密正文或完整任务日志来“补齐”证据；
- 现有真实记录先原字节保护，再做结构规范化；
- 索引缺失、身份漂移、重复、超预算或引用不闭合时失败关闭。

旧能力、SOP 或宿主经验标成 `practiced`、`reliable`、`portable`，但没有满足 1.3 证据闭包时，不得伪造记录，也不能未经逐项核对把所有旧资产一律废弃。保留正文与历史标签作为复核证据，把当前可执行成熟度标为 `needs-evidence` 或把资产置于 `review`；只有新的真实任务验证完成后才恢复相应成熟度。

### 5. 重建启动胶囊

完成实例清单迁移后，使用模型上下文外的严格加载器读取清单，只允许复制 `core/schemas/startup-capsule.schema.md` 登记的小字段，计算准确清单摘要并事务写入 `instance/startup-capsule.toml`。随后回读核对实例 ID、版本、方向、语言、引用和摘要。

普通启动必须证明读取的是胶囊，而不是先把原始 manifest 的展示文字、验证索引、资产正文、私密目录或专业工作区塞进上下文。

### 6. 从合并后的实例真源重建派生物

重建信号地图、时间索引、候选索引及两份看板快照。候选正文必须逐字节保留，只有 `instance/evolution/index.toml` 按已存在候选重建：实例 ID、预算、计数和来源闭合；已实例化助手即使索引为空，`generated_at` 也写本次已授权迁移时间，只有空白模板保持空值。看板 `public` 与 `dist` 快照必须字节一致，并显示迁移后的真实实例名称、版本、方向、正式资产、复核资产、待办和证据状态；目标模板的空态快照只能作为中间物。

## 1.3.1 的验收门

升级只有同时满足以下条件才可交给用户决定是否替换：

1. 官方固定 `v1.3.1` 标签、Release 对象、发布清单和解压后的排序文件树逐路径、逐字节闭合；九个空占位精确通过，其余 `.assistant-*` 内容全部拒绝；
2. 使用维护者构造、覆盖成熟实例关键结构的复杂 1.2.1 合成夹具完成迁移门禁，不只测试 1.3.1 空模板；该门禁证明固定升级契约，不冒充任意真实实例的自动升级器；
3. 实例身份、方向锁、档案、正式正文、治理排期、宿主档案、真实验证记录、登记扩展和本地私密数据没有丢失；
4. 正式资产不存在由 `risk-tiered` 或旧 policy 字段自动授权的情况；
5. 每条可用资产的路线、frontmatter、授权、风险、模型等级、确认门和目标路径闭合；
6. 每个成熟度声明都能在验证索引闭合；不能闭合的只进入 `needs-evidence`／`review`；
7. 普通启动不加载原始实例清单、验证索引、全部地图、资产正文、专业工作区或私密正文；
8. 两份看板快照来自合并后的实例真源且字节一致；
9. 第二次运行零变化；故障注入能够恢复升级前完整实例；
10. 公开候选不含维护者私密工作台、私密发布流程、个人习惯、测试现场、密钥、隐私正文或本机路径。

如果任一门失败，保留原实例并交付冲突说明；不能为了完成升级而降低授权、证据或安全边界。

## 用户实际看到什么

升级前仍先展示一份短预览：哪些模板文件会更新，哪些个人内容会保留，哪些旧资产需要重新确认，哪些成熟度需要在下一次真实任务中补证据。用户不需要打开终端或理解 Schema；宿主 Agent 用普通语言说明选择和后果，得到确认后才执行替换。内部可以做充分、针对性的验证，但普通启动和普通任务不承担升级维护成本。
