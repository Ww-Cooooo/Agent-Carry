# 从 Agent Carry 1.4.8／本地 1.4.9／AI Carry 2.0.0 升级到 AI Carry 2.0.1

## 这次修什么

AI Carry 2.0.0 的升级器会在 `prepare` 和 `confirm` 两个阶段各做一次完整的 GitHub 正式发布核验。这道二次核验本身是必要的，但 2.0.0 错把每次核验都会变化的 `verified_at` 时间写进了用户确认引用。即使 Release、固定标签、公开 `main`、目标整树、发布清单、源实例和写入集合完全没变，第二次核验也会因为时间不同而拒绝刚刚生成的确认引用。

2.0.1 修复的是这一个确定性阻断点，也就是把审计时间与稳定发布事实分开；它不放宽来源、隐私、字节或事务边界：

- 完整审计记录继续保存真实核验时间，前后两次记录摘要可以不同；
- 另生成带 Schema 版本的稳定权威指纹，只包含正式仓库、Release、标签提交、公开 `main`、Git 树、目标文件数、目标整树和发布清单等安全事实；
- 用户确认引用绑定稳定权威指纹，以及源版本、实例身份、组件、工作区、档案和写入集合；
- `confirm` 仍重新执行全部六项 GitHub HTTPS API 核验；任一真实事实、源实例或目标字节变化，旧确认立即失效；
- 单次核验最多六个请求，`prepare` 加 `confirm` 最多十二个。403、超时或网络失败只终止本次升级，不写实例，也不影响 Agent 的对话和其他能力。

## 谁可以直接升级

- 已公开的 Agent Carry 1.4.8；
- 曾保留在本地、从未公开的 Agent Carry 1.4.9；
- 已安装的 AI Carry 2.0.0。

因此，被 2.0.0 确认引用缺陷挡住的 1.4.8 实例不需要先成功安装 2.0.0，可以直接升级到 2.0.1。

## 用户怎么操作

仍从现有 AI Carry 看板的升级入口开始。Agent 运行：

```text
node dashboard/scripts/ai-carry-upgrade-cli.mjs prepare --source <当前实例根目录> --target <已核验的 2.0.1 公开目标根目录>
```

`prepare` 只读检查，并把 `userPreview` 原样解释给用户。用户在下一条独立消息明确回复“升级”或“确认升级”后，Agent 才运行同次返回的 `confirmCommand`。用户不需要操作终端，也不需要理解指纹字段。

## 升级会保留什么

升级保持用户当前打开的实例根路径不变，并逐路径、逐字节保留实例身份、`created_from`、方向、档案、记忆、能力、SOP、经验、候选、验证记录、组件、工作区、本机工具绑定、私密引用、Skill requirements、已安装 Skill、可编辑导出真源、载体、问题报告、任务交接、未来字段和未知文件。

升级不会执行 Skill、组件或工作区脚本，不安装依赖，不联网发现 Skill 新版，不生成问题报告，也不把私密内容送往公开仓库。

## 事务与恢复

1. `prepare` 只读核对来源、目标、发布边界、实例兼容性和预计写入集合。
2. 用户确认后，再次实时核对官方权威，并把目标复制到隔离候选后重新核对整树指纹。
3. 在隔离候选中叠加实例正式真源，重建启动胶囊和两份逐字节一致的快照。
4. 仅事务替换发布清单拥有且字节确实变化的产品文件；所有被替换旧字节进入带清单的回滚包。
5. 任一步失败都按事务记录逆序恢复。失败现场保留供检查，原 Agent 与无关能力继续可用。
6. 成功切换后只执行返回的 `sessionReentryCommand` 核验新运行时；当前会话是否已激活、行为是否已真实验收仍由宿主和用户确认，CLI 不自我证明。

第二次对已经安装且未漂移的 2.0.1 执行检查时，会先核对官方来源、本地静态产品字节、启动胶囊和快照，再返回零变化；不会刷新用户内容、资产、时间或报告。

## 正式发布边界

只有官方 Latest Release、`v2.0.1` 正式 Release、固定轻量标签、公开 `main`、发布清单和解压后的完整目标树一致，并且用户明确选择这一次升级时，2.0.1 才能替换实例。

这份发布清单只为固定 2.0.1 建立条件式升级权威，不授权未来提交、推送、标签、Release、Pages、仓库改名或其他实例操作。
