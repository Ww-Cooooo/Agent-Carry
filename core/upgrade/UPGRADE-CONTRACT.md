# 模板升级机器契约

默认官方更新来源由 `core/upgrade/official-source.toml` 唯一登记。升级输入可以来自该公开仓库正式 Release 标签对应的 GitHub 自动生成源码 ZIP，也可以来自用户指定的本地离线升级包；两者使用同一种发布清单。用户明确指定其他仓库、附件或镜像时，将其标为非官方来源并在读取或下载前取得选择，不从搜索结果自行替换官方源。

1. 只有用户明确提出检查更新时，才读取官方来源并访问网络；不得后台检查、自动下载或强制升级。公开来源不要求用户登录 GitHub。
2. 解析当前实例清单、官方来源记录和目标发布清单。
3. 验证来源身份、正式 Release 状态、轻量标签目标、公开 `main` 与最新正式标签的一致性、清单结构、目标版本、解压后的文件集合、逐文件摘要和路径安全。默认先使用目标标签对应的版本化 ZIP；只有公开 `main` 已证明指向同一标签提交时，才允许使用“最新版 ZIP”。GitHub 可能重新生成压缩容器，因此外层 ZIP 的大小和 SHA-256 只作本次传输记录，不能替代解压内容身份；离线包无需访问 GitHub，但仍按不可信输入检查。
4. 按 `core/ownership.toml` 分类现有内容。实例目录中清单明确列入 `replace_instance_guides` 的固定 `README.md` 原则上属于目标模板说明；但替换前必须先检查实例清单和地图是否把其中某一份作为用户正文引用。若存在实时引用，先执行目标发布清单的版本化迁移：逐字节复制到用户拥有路径、核对摘要、更新引用并回读成功，之后才能把原路径替换为目标说明。目标路径已有不同内容、引用语义不明或摘要不一致时停止并显示冲突，不能覆盖或猜测合并。同目录的其他文件、用户新增子目录、迁移后的档案和本地私密层不得因名称相似被替换。
5. 生成预览，不写文件：列出当前版本、目标版本、来源、替换、迁移、保留、删除、冲突和不兼容扩展。
6. 用户选择保留现状或迁移升级。
7. 迁移升级先创建本地临时回滚副本，再在临时目录组装新核心和保留资产。目标模板文件必须来自已经固定身份的发布内容清单或可信目标提交的允许集合；发布清单中的 `**` 是选择约束，不是对开发工作树做无边界递归复制的命令。`.git`、`node_modules`、缓存、临时构建目录和维护者私密层即使位于匹配目录下也不得进入候选。先执行发布清单中的 `migration_rules`，再放入目标模板核心和精确目录说明，最后恢复或迁移个人资产；逐路径证明除说明与有依据的 Schema 迁移外，用户资产和实例档案没有被覆盖。对旧版把 `instance/profile/README.md` 作为 `profile.user_preferences_ref` 的实例，先把该文件逐字节迁移到 `instance/profile/approved-profile.md`，核对摘要并更新引用，再替换目录说明。把所有 `asset_kind="task-family"` 路线的 `state` 规范为 `on-demand`，其他字段不借机改写。检查实例方向锁、实例展示名、交流方式兼容、学习政策、资产风险／授权／成熟度兼容、地图目标、长期治理卡、跨会话控制修订、触发注册表、唤醒胶囊、非启动时间索引、宿主接入协议／Schema、看板动作/快照与扩展接口。旧实例缺少 `profile.guidance_mode` 时按 `balanced` 读取，补字段不得改变锁定方向。正式动态状态、延期卡和不含秘密的宿主档案保留；长期治理卡按稳定 ID 使用目标模板正文并迁移实例的启停、锚点、完成、到期、延后和触发修订字段，ID 缺失、重复或语义冲突时停止自动合并。两个信号派生投影从合并后的状态元数据重建；旧资产的新字段只在相关资产被使用、修改或复核时渐进补齐，宿主能力在下次相关使用时重新验证。旧宿主档案缺少“模型选择／实际路由／辅助模型／自动上下文”字段时按 `unknown` 保持可读，不为补字段扫描宿主、日志或记忆正文。
8. 原子替换目标文件；失败时恢复回滚副本。
9. 在替换前后分别运行确定性语义检查：所有地图目标存在；正式 `active`、`provisional`、`review` 记忆／能力／SOP／经验有类型一致的直接路线；`task-family` 全部为 `on-demand` 且不计资产；实例状态下没有任何用户档案继续引用将被替换的目录说明；启动仍只读取声明的极小入口。第二次对同一候选执行迁移不得继续产生差异。
10. 用户验收后删除临时回滚副本。

若核心被用户自定义且无法安全套用清单，默认不做逐行自动合并；转为“新模板实例 + 迁移个人资产”。
