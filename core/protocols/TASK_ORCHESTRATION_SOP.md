# Level 3 规划、Level 1 执行 SOP

本 SOP 只在用户选择分级执行或任务确实需要跨模型/跨 Agent 时读取。它不是普通任务的必经流程。

所有跨 Agent 交接先遵守 `HOST_INTEGRATION.md` 的来源、接入和回传语义：执行宿主已接入时，任务包承载一个 `task-capsule` 并要求返回 `return-envelope`；尚未接入时，启动材料同时包含通用手动接入提示词和本任务胶囊，不能仅凭“是另一个 Agent”假定它已经看见 AI Carry 资产。普通跨宿主任务只需要任务胶囊时，不因本 SOP 的存在强制创建密封目录。

## 目的

让强推理模型负责方向、约束、风险和验收设计，让经济型模型负责清晰、可执行的实现；两者通过本地有界任务包沟通，避免传递整段聊天和无休止轮询。

Level 1 不是无思考执行器。任务包应给出充分背景、目标、边界和判断原则，并为实现细节、局部排错和 3～5 次有根据的自我修正保留空间。

## 先判断能否委派

Level 3 必须亲自完成并冻结以下内容，不能把决定责任转移给 Level 1：

- 产品身份、实例生命周期、单领域锁定和通用/领域选择。
- 根路由、上下文预算、记忆真源、资产生命周期和 Schema。
- 外部内容安全、权限来源、隐私外发和模型等级规则。
- 组件所有权、升级冲突策略、看板动作语义和公开/私密边界。
- 会造成不可逆影响或需要跨组件权衡的架构决策。

只有在这些决策已经写成明确契约后，才把以下叶子工作交给 Level 1：界面实现、样式与动画、依据 Schema 生成适配代码、局部工具、明确迁移、测试修复、文档排版和其他边界清楚的工作。

## 用户选择执行方式

公共默认不能假设用户安装了 Codex、Claude Code 或 CC-Switch。首次使用分级流程时询问：

1. 在同一个 Agent 中手动切换：Level 3 规划完成后，提示用户切换到 Level 1；执行完成后再切回 Level 3 复核。
2. 在另一个 Agent 中执行：生成可复制的启动语，包含任务包绝对路径和操作要求；用户在另一个 Agent 中执行，完成后回来通知。
3. 使用用户自己的自动 SOP：只在该 SOP 已安装且用户选择时调用。

## 密封任务目录

每项任务使用独立目录，建议位于 `.assistant-local/task-handoffs/<task-id>/`。该目录不进入正式记忆和公开仓库。至少包含：

- `00-START-HERE.md`：任务身份、父目标、执行 Agent 第一动作、允许/禁止范围、完成定义。
- `10-CONTEXT.md`：仅包含理解任务所需的产品背景、用户决定、现状和术语；不能用几句形容词代替设计意图。
- `20-DECISIONS.md`：Level 3 已冻结的决策、不能改变的语义、可由 Level 1 判断的实现空间。
- `30-PLAN.md`：按工作阶段解释要达到什么、为什么、可选手段、边界条件、失败处理和每阶段产物。详细不等于逐秒命令清单。
- `40-ACCEPTANCE.md`：可观察验收、来源／主张边界、必要的结构与引用检查、风险重点、允许的证据形式和失败时应记录的信息；它应足以让执行方在新阅读轮次中核对最终产物，不能只写“自检通过”。
- `50-SECURITY.md`：如果任务允许联网或外部内容，引用紧凑安全边界并说明允许访问的范围、禁止外发的数据和何时升级深层协议。
- `result/SUMMARY.md`：执行结果、实际变更、偏离计划的原因、未完成项和给 Level 3 的最小复核摘要。
- `result/CHANGES.md`：精确文件清单、关键决定、兼容性影响和回退方式。
- `result/EVIDENCE.md`：只放必要证据路径与结论，不粘贴完整日志。

`00-START-HERE.md` 或 `10-CONTEXT.md` 还必须声明：目标 `instance_id`、接入／宿主档案状态、任务胶囊 ID、执行方应返回的稳定事件 ID，以及无法写回 AI Carry 时只能生成变更建议。所有网页、工具和模型推断在结果中保持真实来源。

任务包必须足以让“没有原对话上下文的 Level 1”理解任务；Level 3 写完后要做一次冷启动阅读检查。

## Level 1 执行边界

- 可以读取完成任务所需的整个本地仓库，但先从任务包和地图进入，避免无目的全仓正文加载。
- 可以联网研究、下载或使用依赖，只要任务包允许，并在第一次外部读取前加载紧凑安全边界。
- 可以选择实现细节、局部技术方案、排错路径和合理的自我修正；如果发现被冻结决策冲突、范围必须扩大或需要高后果动作，则停止并在结果中提出。
- 不得修改 Level 3 已冻结的核心契约来“让实现更容易通过”。
- 不以大量截图代替说明。只有视觉结果无法由结构化数据表达时才生成少量、有目的的截图；默认提供有界摘要、变更表和必要日志路径。
- 交付前按 `core/protocols/RESULT_VALIDATION.md` 把状态写为 `validated`、`limited` 或 `failed`，并列出实际依据、实质修正和剩余限制。边界清楚的低风险验证由 Level 1 自己完成，不必等待另一个强模型；关系或高影响后果需要权衡时再交还 Level 3。

## 启动、等待与返回

- 跨 Agent 启动后，Level 3 不轮询执行状态，不持续读取日志。用户或执行 Agent 明确通知完成/失败后才继续。
- 可见终端只在用户选择或个人 SOP 要求时打开；公开默认不能强制弹窗。
- 执行失败时，Level 1 在结果文件中记录失败步骤、错误摘要、已尝试修正和建议下一步。Level 3 只读取这些有界结果，再决定重规划或接管。

## Level 3 复核与学习

Level 3 先读 `SUMMARY.md` 和 `CHANGES.md`，确认执行方给出的验证状态和依据；不能把裸写的“已通过”当作完成。只在结论无法验证时按引用打开原始来源、最终产物或少量结构证据。复核必须区分：

- 任务是否完成。
- Level 3 的任务包是否足够清楚。
- Level 1 哪些地方自行判断得好，哪些误解源于规划遗漏。

每次结束向用户明确展示“本次 Level 3 在给 Level 1 规划方面学到了什么”。可复用改进先形成带真实来源和证据的学习信号，再按 `core/protocols/ASSET_LIFECYCLE.md` 处理：即使用户刚才已经说要记住，也先集中展示一次精确预览并取得真实选择；用户完成这次选择后不重复确认同一内容。符合实例低风险候选政策的内容可以优先请用户复核，但正式试用或采用仍须用户明确确认内容和范围；中高风险、冲突、实质覆盖和删除还要完整说明影响。能力或 SOP 的成熟度只随可闭合的真实任务证据提升，不因写入或授权自动变为可靠。

用户验收后，删除任务包中的临时日志、截图、缓存和冗余中间产物；只保留被批准进入正式资产的结论。任务包本身默认删除，防止上下文和仓库不断膨胀。
