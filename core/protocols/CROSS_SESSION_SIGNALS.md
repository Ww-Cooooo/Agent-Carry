# 统一触发内核与跨会话信号

本协议只在以下情况读取：启动胶囊显示到期、待处理、不确定、溢出或待恢复状态；当前任务产生了需要跨会话累计的真实事件；用户要求检查、重建或解释触发系统；开发者新增或修改“达到某条件后做某事”的规则。普通任务不加载本文、完整规则或全部动态状态。

## 目标

AI Carry 必须知道“什么时候该做什么”，但不能为此把所有规则和状态塞进每次启动。统一触发内核把静态判断、动态状态、启动投影和目标正文分开，使时间、次数、风险、规模、状态、版本和恢复条件都能使用同一套治理边界。

它不是后台守护进程、任务队列、数据库或第四层内容路由。第一版由当前宿主 Agent 在真实事件和少量检查点执行；Markdown/TOML 仍是可迁移真源。

## 一条触发规则必须回答什么

任何“达到 X 后执行 Y”的设计，都必须在 `core/maps/trigger-registry.toml` 登记并明确：

1. **触发类别**：当前事件、动作门禁、跨会话累计、定时、健康指标、使用时校验、事务恢复或消费者本地检查；
2. **检查点**：在请求到达、动作之前、任务结束、资产变更、失败发生、启动或使用某能力时判断；
3. **正式所有者**：谁定义阈值、分支、门禁和完成标准；
4. **动态状态所有者**：是否需要跨会话保存，保存在哪里；
5. **启动策略**：不投影、只投影异常，还是只投影最早时间与总数；
6. **处理路线**：命中后读取哪个分类地图和目标规则；
7. **门禁**：是否需要用户确认、更高模型或安全协议；
8. **清理与失败**：何时压缩、归档、删除，以及中断后如何恢复。

新增业务规则通常只登记到注册表和所属领域，不得顺手向 `BOOTSTRAP.md` 增加完整条件。只有出现现有类别无法表达、且所有任务都必须识别的新型全局事件时，才允许评估是否修改启动入口。

## 触发类别与上下文策略

| 类别 | 例子 | 何时判断 | 是否跨会话保存 | 普通启动看到什么 |
| --- | --- | --- | --- | --- |
| 当前事件 | 用户要求导出、形成 SOP、修改组件 | 事件发生时 | 否 | 无 |
| 动作门禁 | 联网、向额外接收方敏感外发、秘密读取、删除、发布、资产激活或成熟 | 后果发生前按风险政策；秘密进入模型或消息正文直接禁止 | 通常否；未解决时才保存 | 未解决异常的短路线 |
| 跨会话累计 | 用户已允许“先观察”的同类候选反复出现，或正式方法重复成功／失败 | 新证据出现时 | 是 | 学习卡只引用候选稳定 ID 与 source revision，不复制主张／别名／范围；仅临近、命中、冲突或不确定项投影；未授权的首次学习发现不写候选、正式资产、信号或提醒 |
| 定时 | 180 天治理、延期模型任务、用户要求的候选提醒 | 启动只比较最早时间；改期和完成时更新 | 是 | 最早唤醒时间和总数 |
| 健康指标 | 记忆漏检、资产规模、地图溢出 | 相关读写或失败发生时 | 需要累计时保存 | 达到评估条件后才出现 |
| 使用时校验 | Skill、宿主能力、路径、权限或版本变化 | 实际使用或明确刷新时 | 发现未解决问题后才保存 | 未解决异常的短路线 |
| 事务恢复 | 写状态成功但投影中断 | 启动和下一次写入前 | 是 | 控制记录的固定字段 |
| 消费者本地 | 看板快照新鲜度 | 看板自身 | 由消费者管理 | 不进入 Agent 启动 |

`expected_next_use` 只是资产保留与生命周期判断的依据，不能因为填了日期就自动变成提醒。确需提醒时必须另有明确的 `next_check_at`、`next_due_at` 或 `remind_at`，并进入定时投影。

## 四层信息严格分离

1. **极小全局检查点**：`BOOTSTRAP.md` 和入口规则只识别少量稳定事件族。
2. **触发注册表**：`core/maps/trigger-registry.toml` 完整盘点规则归属，但普通启动不读取。
3. **动态状态与派生索引**：资产 frontmatter、`instance/signals/` 和非启动时间索引保存或投影当前进度。
4. **目标规则与正文**：只有命中路线后才读取。

完整规则不靠隐藏在自身正文中的一句“何时读取我”触发。上一级地图、当前动作检查点或启动胶囊先提供足够的短元数据，然后逐层展开。

## 启动只读唤醒胶囊

`instance/maps/signal-map.toml` 的角色是**唤醒胶囊**。启动时与控制记录一起读取，但它只能包含：

- 控制与源修订是否一致；
- 已经接近处理、需要处理、冲突、不确定、过期、溢出或待恢复的少量路线；
- 所有未来定时项中的 `next_wakeup_at`；
- 定时项总数和非启动时间索引的一个稳定引用；
- 每条可见路线的短原因、门禁和下一路线。

它不得包含：所有观察中信号、每一条未来日程、完整规则、资产正文、证据原文、全部质量指标或所有宿主能力。

启动判断固定为：

1. 只读取 `assistant.toml` 的 `[signals].startup_reads` 明确列出的控制记录和唤醒胶囊。`projections` 表示事务更新集合，不是启动读取集合；不得为了确认最早时间而预读 `time_projection` 或枚举 `source_root`。
2. 控制状态不是 `clean`、修订不一致或文件不可解析时，只进入定向恢复。
3. 有可见路线时，只处理与当前请求相关或优先级最高的一条；不批量加载所有目标。
4. `next_wakeup_at` 为空或晚于当前时间时，不读取时间索引和任何定时卡正文。
5. 当前时间达到或超过 `next_wakeup_at` 时，只读取 `instance/maps/time-trigger-map.toml`，筛选到期元数据，先给用户一个固定长度聚合提醒；用户选择具体项目后才读取目标卡。
6. 所有检查都未命中时，立即继续普通三层路由。

以后新增十条、百条定时规则，只会让非启动时间索引增长；启动胶囊仍只增加一个最早时间和一个总数，不按规则数量增长。

## 时间触发怎样可靠工作

时间触发的真源是目标卡的小型时间字段，`instance/maps/time-trigger-map.toml` 是可重建的非启动索引，唤醒胶囊只保存它的最小聚合。

每个时间触发至少保存：稳定 ID、状态、正式来源、`next_check_at` 或等价字段、路线、目标修订、模型等级和确认门。时间使用带偏移量的 ISO 8601 时间，不能依赖文件修改时间、聊天历史或模型猜测。

创建、改期、暂停、完成或删除定时项时：

1. 先更新正式来源的时间字段和修订；
2. 刷新非启动时间索引；
3. 重新计算全部有效定时项中最早的 `next_wakeup_at` 和总数；
4. 刷新唤醒胶囊并校验修订；
5. 全部成功后才结束更新事务。

周期任务完成后，以**实际完成时间**加 `frequency_days` 计算下一次，不从原计划时间反复累加，避免长期漂移后一次出现多个补跑。暂停或用户明确推迟时使用 `snoozed_until` 计算有效检查时间，但不覆盖原始到期时间。

核心没有后台执行能力，因此“180 天到期”的精确定义是：

- Agent 当时正在运行：在第一个可用检查点识别；
- Agent 当时关闭：在此后的第一次启动识别；
- 到期只产生提醒，不自动联网、不自动执行治理、不自动切换模型；
- 用户若需要离线期间准点通知，可选择宿主或系统定时插件，但它不是 AI Carry 可用性的前提。

## 累计、同类与阈值

每次只处理当前真实事件，不在启动时扫描全部记忆：

1. 为事件记录稳定 `event_id`、真实来源、任务事件 ID、与任务分开的实质情境 `context_id`、真实发生时间和是否独立。任务发生后再到自然停点确认学习是正常顺序，不能为了通过校验伪造新的发生时间。
2. 根据事件类别只进入 `instance/signals/<family>/` 的相关状态，或目标资产的小型元数据；不枚举其他类别。
3. 通用状态先按资产类型、作用对象、核心主张、范围、条件、时间和别名缩小候选。学习累计是例外：首次发现必须先在自然停点询问，用户允许“先观察”后，状态卡只按已获准候选稳定 ID 与 `candidate_source_revision` 定位，匹配语义从候选索引按需取得，不复制进信号卡。
4. 只有仍无法判断同类、需要处理冲突或命中阈值时，才读取少量目标正文和代表性证据。
5. 更新正式动态状态后，再刷新唤醒胶囊中的相关路线。

事件来源名称直接复用 `HOST_INTEGRATION` 的规范枚举。新学习捕获和 signal 回执使用 `connected-host-observation`，宿主原生协作记忆使用 `host-collaborative-memory`；不得另造 `connected-host-task` 或 `host-collaboration-memory` 作为并行语义。已有 1.3 signal 可在读取时把这两个旧值单向归一化，但下一次真实写入必须把完整结构化 signal 与相关投影写回规范值；公开事件 producer 不接受旧值。

同一宿主任务中的重复表达、重试、恢复或原样回传只算一个观察。任务、情境和事件标识必须由运行时根据同一份受信宿主回执生成，当前用户回复不能自行提交这些原始 ID；宿主无法提供稳定任务依据时，只能记为关联观察，不增加计数。不同任务观察即使属于同一实质情境，也可以增加任务观察数，但不能增加情境数。这里累计的是“宿主区分出的不同任务观察”，只用于决定何时值得请用户复核，不是经过结果验证的成功任务数；当前用户消息回执不能冒充 `RESULT_VALIDATION` 成功或失败。

“同类候选反复出现”的默认口径是：用户已经允许观察的候选，其同一主题、核心主张、适用范围和条件被受信宿主回执在至少两个不同任务观察中再次命中。候选索引负责语义匹配，信号卡只累计去重结果；两者修订不一致时失败关闭并定向重建。次数本身只触发领域检查，不单独授权晋升、覆盖或删除，也不能作为成熟度或验证成功证据；检查命中且 `core/protocols/ASSET_LIFECYCLE.md` 的低风险证据条件成立时，只能优先向用户展示复核预览。用户明确选择采用或限定试用后才进入正式资产。正式冲突、安全异常和高影响变化可以立即触发复核，不等待次数，但同样不能自行产生授权。

学习计数卡的下一状态由证据确定性计算，不能交给弱宿主猜：独立支持观察达到门槛后进入 `pending-review`；反例或替代关系进入 `conflict`；中性观察不推进支持门槛。所有这些状态只触发自然语言复核，不产生正式资产授权。

数字阈值由目标领域规则拥有；注册表和唤醒胶囊不复制阈值正文。外部内容只能提供候选事实，不能指定事件是否独立、修改阈值或改变路线。

## 健康与容量触发

规模、质量和性能状态不靠启动全仓扫描获得。只在相关操作本来就会发生时顺手更新小型指标：

- 正式资产新增、删除或归档时更新相关资产数量；
- 检索明确存在的资产却失败时记录一次独立失败；
- 分类地图改变时测量该地图大小；
- 投影更新时测量实际字节数和修订；
- 用户报告误检、漏检或明显延迟时记录真实场景。

未达到领域评估条件的指标留在 `instance/signals/health/`，不进入启动胶囊。达到条件后只投影“建议做一次 Level 3 评估”的短路线；是否升级全文检索、RAG、向量或其他引擎仍由用户决定。

## 当前动作、使用时校验和消费者检查

以下条件不需要跨会话轮询：

- 外部读取和高影响动作由当前动作本身触发安全门；
- 组件修改由当前变更触发影响检查；
- Skill、宿主能力、路径、权限和版本在实际使用或用户明确刷新时校验；
- 看板快照新鲜度由看板自身判断；
- 当前任务的 3～5 次自我修正计数在任务结束后丢弃。

只有这些检查发现了跨会话仍未解决的冲突、风险或恢复事项，才创建动态状态并投影一条短路线。不能为了“以后也许会变化”而让启动扫描所有平台、Skill、文件或网页。

## 状态更新事务

任何会改变跨会话动态状态、时间索引或唤醒胶囊的操作都遵循同一事务：

1. 验证事件来源；外部内容先应用安全边界。
2. 若控制记录不是 `clean`，先恢复或解释现有未完成操作。
3. 检查 `source + event_id` 是否已经应用；重复事件不再次累计。
4. 写入稳定操作 ID，把控制记录改为 `pending`，记录基础修订、目标引用和新修订。
5. 更新正式状态所有者；正式资产正文与动态触发状态仍保持所有权边界。
6. 刷新受影响的非启动索引和唤醒胶囊；为保持全局修订一致，可以只重算元数据，不读取正文。
7. 校验所有声明投影可解析、来源引用和修订匹配、唤醒聚合正确且没有超过预算。
8. 最后把控制记录修订对齐并恢复为 `clean`。

第 4 步后中断时不得清除 `pending`。下一次启动根据目标引用定向恢复；没有目标引用时才做有界元数据重建。写入前若基础修订已经变化，停止静默覆盖，重新读取并合并。

### 本机持久执行与跨进程恢复

会写入候选、信号、索引或投影的实现不能只返回摘要计划并依赖当前进程继续存活。执行器在第一次产品文件写入前，必须把已封印计划、每个写目标的逐字节 preimage 和每一步的逐字节 proposed bytes 作为一个目录级原子 bundle 保存到 `.assistant-local/runtime/cross-session-signals/`。该目录是本机操作恢复材料：

- 不属于正式资产、启动读取、信号真源、看板公开内容、导入导出、隐私迁移或发布集合；普通启动仍只读实例清单、控制记录和极小唤醒胶囊；
- 对外计划和 CLI 摘要继续保持 `contentIncluded=false`，不得输出正文、base64、绝对位置或 bundle 文件名；
- bundle 必须同时绑定 public/dist 两份看板快照的旧字节与同一份新字节。新快照先在有界隔离投影中合并全部当前真源与本次 proposed bytes，再用正式快照生成器重建；不能在旧快照上局部拼接一张卡；
- 写入顺序固定为 `control-pending → 正式状态与派生索引 → dashboard/public → dashboard/dist → control-clean`。每一步使用同文件系统的原子替换、逐字节回读和真源摘要检查；任一步失败都保留 bundle 与 `pending`／精确前缀，不伪装成功；
- 独立进程只能把现场识别为 `preimage`、`final`、合法步骤前缀或 `drift`。`resume` 只从合法前缀继续，`rollback` 只把合法前缀恢复为全部逐字节 preimage；`drift` 不自动覆盖。完全 final 不通过崩溃回滚倒退，完全 preimage 和 final 都可幂等关闭；
- TTL cleanup 与显式 close 只可删除已经核对为完整 preimage 或完整 final 的本机 bundle。合法前缀必须保留并报告需要 resume/rollback；任何目标、真源、临时原子替换材料或 bundle 漂移必须保留并报告定向恢复；
- 公开 CLI 只提供有界 `inspect`、`resume`、`rollback`、`close`、`cleanup`，stdout 是固定小摘要。初次计划仍必须来自同进程受信宿主观察与当前用户消息回执，不能由 CLI JSON 自行提交事件、正文或任意写集。

隔离快照投影位于当前仓库的父目录，只能使用 signal runtime 自有且含仓库绑定摘要的前缀，并在 hardlink 真源前写入物理 owner marker。相关事务构建和显式 signal cleanup 可有界清除 PID 已死亡、marker 与仓库绑定完全匹配的遗留投影；删除前必须验证整棵投影没有 symlink／reparse point，并逐项解除 hardlink 后自底向上移除目录。未知目录、其他仓库目录、伪造 marker 或链接必须原样保留且不得跟随。普通启动不得做这项父目录扫描。

事务到达 final 后，执行器必须再次用正式合并真源生成器核对 public/dist 字节一致且第二次构建为零差异。`pending-review`、`conflict` 等真实候选／信号变化因此与看板 source digest 和可展示候选投影在同一事务内同步；不能等到下一次手工刷新才补快照。

## 可见状态和投影边界

动态状态可以是：

- `observing`：继续在领域内累计，默认不进启动；
- `near-trigger`：下一次相关事件很可能命中，可投影；
- `pending-review`：已达到检查条件；
- `conflict`：存在不可静默合并的冲突；
- `uncertain`：来源、同类判断或写入结果不充分；
- `stale`：超过验证窗口或基于旧修订；
- `resolved`、`rejected`、`archived`：退出启动投影。

投影条目只含稳定 ID、短原因、进度、下一触发语义、路线、来源状态、真源修订、模型等级和门禁。完整正文和外部原文永不复制进投影。

## 大小预算与溢出

唤醒胶囊预算来自 `assistant.toml`，当前为 1536 字节。超过预算时：

1. 不静默截断高风险、冲突、不确定或恢复路线；
2. 删除结束项，退回普通观察项，按领域合并同一处理路线的短摘要；
3. 仍超限时保留每个受影响领域的一条聚合路线；
4. 设置 `overflow = true` 和 `state = "overflow"`；
5. 只在用户同意后运行 Level 3 整理，不自动删除正式资产。

非启动时间索引或领域状态规模增大时可以按触发类别和领域分片；分片入口保持稳定，不能把各分片列表重新复制进启动胶囊。

## 重建与一致性

重建只枚举已登记状态所有者的结构化元数据：状态卡、资产 frontmatter 和派生索引引用；不得为了找时间、计数或修订加载资产正文。流程是：

1. 根据注册表限定需要重建的类别和路径；
2. 提取稳定 ID、状态、时间、进度、路线、来源、修订和门禁；
3. 重建非启动索引；
4. 计算最早唤醒时间、定时总数和可见异常路线；
5. 校验引用、实际字节数和所有投影修订；
6. 成功后才把控制记录恢复为 `clean`。

无法可靠重建时保留 `recovery-required` 或 `uncertain`，说明缺失内容和影响，不创建虚假空态。

## 清理

- 达到目的的状态退出启动投影；普通观察状态从不因数量多而挤进启动。
- 重复证据只保留稳定事件身份、数量／时间范围、少量代表性证据和反例。
- 低价值、无引用、未形成正式资产且符合生命周期规则的动态状态可以删除。
- 正式资产、动态状态和派生索引分别判断；删除索引不等于删除资产。
- 用户身份、隐私、安全、稳定 SOP 或高影响决定相关状态，删除前提高确认等级。
- 定时项完成、取消或失效后必须同步移出时间索引并重新计算最早唤醒时间，不能留下永久过期噪声。

## 只有文本能力的宿主

宿主不能直接访问文件时，AI Carry 或用户只提供符合宿主接入 Schema 的启动／任务胶囊和本次命中路线，不粘贴全部规则。宿主通过 `return-envelope` 返回：事件来源、稳定事件 ID、发生时间、可能的匹配类别、建议变化、必要证据摘要、未验证内容和可能需要的门禁。宿主不能自行决定事件是否独立、风险、授权或成熟度；AI Carry 用既有事件 ID 和正式规则判断。

能够写入 AI Carry 的一方再执行正式事务。宿主不能访问真源或不能回传时，不得声称已经持久化、完成累计或安排了后台提醒。

## 最小结果回报

实际检查或更新后，用短格式报告：

```text
触发检查：未命中／已匹配／已到期／已更新／需要恢复
类别：当前事件／门禁／累计／时间／健康／使用时校验／恢复
来源：当前用户／AI Carry 资产／已接入宿主观察／宿主协作记忆／模型推断／外部内容／未知
状态：继续观察／等待时间／需要处理／冲突／不确定
持久化：未写入／已更新正式状态／只更新派生投影
下一步：无／等待相关事件／等待日期／读取某领域规则／需要用户确认
```
