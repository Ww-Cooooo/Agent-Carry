# 助手组件变更联动

本协议仅在新增、修改、删除、重命名、移动、升级或优化 Agent Carry 本身时读取。普通工作和普通资产使用不加载它。

## 目标

任何功能变化都必须在所有相关入口、路由、Schema、看板投影、升级说明和人/Agent 文档中保持同一语义；不能只修局部后让其他部分继续按旧版本运行。

## 变更流程

1. 在 `core/maps/component-map.toml` 找到正式组件和唯一所有者。
2. 沿 `depends_on` 和 `projects_to` 形成有界影响清单；不要靠全仓正文猜测，但可用文件引用搜索验证清单是否遗漏。
3. 先改正式所有者，再依次更新：入口与地图、引用方、Schema/示例、看板动作或快照、升级清单、面向用户文档。
4. 新增组件必须登记 ID、所有者、路径、依赖、投影和普通上下文策略；删除或移动组件必须清除所有旧链路。
5. 新增或修改“达到某条件后做某事”的行为时，在 `core/maps/trigger-registry.toml` 登记类别、检查点、所有者、动态状态、启动策略、路线、门禁、清理和失败行为。除非出现无法由现有类别表达的全局事件，不得把具体规则追加到启动入口。
6. 根据风险进入 `core/protocols/RESULT_VALIDATION.md`：文字说明核对来源与引用；Schema 做解析和最小样例；地图检查稳定 ID 与真实目标；派生投影核对正式真源；高风险升级或安全规则做针对性场景。只有最终状态为 `validated` 才宣布正式变更完成；个人项目不要求每次运行庞大企业级回归。
7. 向用户展示紧凑结果：检查了哪些组件、预期是什么、是否合格、仍有哪些例外。详细清单可写入看板快照，不在聊天中重复大段文本。

任何检查系统本身也可能老化。长期治理 TODO 研究的是“如何改进一致性体系”，不是替代本流程；每次真实变更仍必须当场完成联动。
