# AI Carry 正式修改质量原则

本协议只在准备改变 AI Carry 正式内容时读取；讨论、只读检查、普通任务和临时草稿不加载。

## 四项最高原则

1. **小故障不能拖死整个 Agent。** 能唯一修复就局部修复并继续；不能确定时只隔离当前变化或能力。只有身份、用户数据、秘密、私密边界、所有权或正式切换真源不可信，才停止对应高风险动作。
2. **全面思考和设计。** 主动考虑用户体验、未来变化、升级、容错、隐私、回退和模块关系，不能因为追求轻量而少想或遗漏必要功能。
3. **主动精简、轻量落地。** 优先复用、合并和删除；没有新的真实职责，就不增加框架、协议、状态机、登记表、字段或测试矩阵。
4. **不要把“全面思考”实现成“全面管控”。** 想到的风险先用于判断和收敛，不逐项变成全局门禁。协议约束真实结果和硬边界，不锁死说明文字、字段顺序、时间戳、计数或可重建投影。

四项原则只决定怎样完成当前已授权工作，不扩大写入、联网、外发、Git、发布或破坏性动作授权。

## 最小变更闭环

一次正式修改只需要闭合四件事：

1. **找到所有者和影响范围。** 从 `core/maps/component-map.toml` 找到负责当前事实的组件，只沿真实依赖和引用展开；不用全仓扫描代替所有权判断。
2. **修改最小真源。** 先改唯一正式来源，必要消费者随同更新。实例变化同时使用 `INSTANCE_EVOLUTION_COMPATIBILITY.md`，默认保留实例身份、用户内容、私密／本机层和未知内容。
3. **验证受影响的用户旅程。** 普通文字或局部实现只做直接回读；身份、用户数据、升级、迁移、公开发布等高风险变化才增加隔离候选、回退或故障反例。没有被本次变化影响的能力不做全量回归。
4. **说明真实结果。** 报告修了什么、故障范围、保留内容、实际验证和下一步。候选、提交、推送与发布分别说明，不能互相冒充完成。

现有结构足够承载时，到这里结束。只有确实出现新的长期职责，才登记新组件或新协议；新增机制应替代或合并旧复杂度，不能只叠加。

## 写入与失败范围

- 文件数量不决定事务大小，语义耦合才决定。身份或必须同时成立的用户数据用小型原子事务；彼此独立的文件各自写入，一个失败不回滚已经验证且不依赖它的结果。
- 胶囊、索引、快照、计数、报告和缓存属于可重建投影。真源成功后再刷新；刷新失败只标记相关区域待重试，不撤销有效真源。
- 旧格式、未知字段和无法安全理解的内容原样保留。能从可信真源唯一推导的缺项可以自动补全；所有权或正文冲突只隔离当前项。
- 摘要只用于发布候选、迁移包、Skill 包、升级前像等确实需要绑定字节的边界。时间只用于真实日程和审计；不能因为格式、空值或普通漂移单独阻断召回、对话和无关能力。
- 路径逃逸、秘密外泄、执行不可信脚本、无声覆盖用户数据和私密内容进入公开层仍是硬边界，但默认也只阻止当前动作。

## 组件、实例与发布

- 模板／核心变化：更新所有者和确实受影响的入口、地图、Schema、文档或派生物；新增路径在提交前归类为公开产品、私密排除或本地不入库。
- 实例资产：使用正文和直接路线作为真源，索引和看板按需重建。独立组件只有现有资产或扩展无法表达时才登记，不能为每项学习内容复制一份组件记录。
- 升级与迁移：只在现有用户会得到不同结果时增加版本迁移；验证新核心、用户内容、受影响能力和回退，不枚举无关组件。
- 公开发布：从固定私密提交生成工作区外候选，验证公开允许／拒绝边界、私密材料为零和本次关键用户旅程。历史发布证据不重复参加当前运行门。

完成标准是用户可观察结果成立、数据和硬边界可靠、故障停在合理范围。检查器本身失败时，只有覆盖同一结果与安全边界的直接证据才能替代；身份、用户数据、隐私和公开边界不能靠推断降级，也不能为了追求“全绿”再增加一套检查系统。
