# Agent Carry 正式修改质量原则

本协议只在准备对 Agent Carry 的正式内容执行新增、修改、删除、重命名、移动、迁移、升级、优化或发布时读取。正式内容包括模板／核心组件、Schema、地图、协议、看板契约、升级与发布材料，也包括实例身份、正式资产和正式动态状态。只读检查、普通任务、既有资产的正常使用、尚未决定落盘的讨论和可丢弃临时草稿不加载本协议。

## 1. 不可颠倒的优先级

1. 问题必须从根因上修好；
2. 用户数据和使用可靠性必须得到证明；
3. 在前两项成立后，再减少无意义的流程和用户负担。

“轻量化”不能理解成少写必要规则、少做必要验证或勉强打补丁。它表示：内部可以有充分且针对性的检查，用户不需要理解和手动操作这些检查；不引入与风险无关的企业级流程，也不让每次普通启动和普通任务承担维护成本。最终目标是：**内部修得扎实，用户侧仍然清亮。**

不能为了显得严谨而增加无关审批、后台服务、常驻扫描、多个终端或每次任务都要运行的全量回归；也不能为了显得轻量而省掉根因、数据保护、回滚和真实结果验证。

## 2. 命中与模型等级

- 启动入口只保留“即将发生正式持久变更”这一事件族。命中后才从 `assistant-maintenance` 加载本协议；该入口允许 Level 1 读取共同质量原则，但不因此获得高影响写入权限。完成后不把检查清单投影到下次启动。
- 模板、核心、Schema、路由、安全边界、升级、发布和跨组件架构必须由 Level 3 负责判断与验收，不能把重要架构整体交给 Level 1。
- 实例记忆、能力、SOP、经验和状态的正式变更，同时读取 `ASSET_LIFECYCLE.md`；稳定低风险更新可以按其中的模型等级执行，但仍使用本协议的根因、影响、验证和回退原则。不能因为本路线名为“助手维护”就要求每次保存、纠正或停止一条普通习惯都切换 Level 3；只有目标类型、风险或歧义真正达到高等级门槛时才升级。
- 实例安装、更新、删除软件／Skill／模型／组件，或学习、进化和配置产生任何正式持久变化时，同时读取 `INSTANCE_EVOLUTION_COMPATIBILITY.md`。它复用当前动作授权，只核对所有权、接口和升级闭包；原生资产不重复建组件清单，普通用户也不增加一轮兼容确认。
- 只读检查不会因为发现问题而自动获得写入授权。检查结论、修复候选、模板吸收、Git 提交、推送和发布是不同动作，分别服从各自门禁。

## 3. 两条有界影响路线

### 模板与组件

1. 在 `core/maps/component-map.toml` 找到正式组件和唯一所有者。
2. 沿 `depends_on` 与 `projects_to` 形成有界影响清单，再用引用搜索检查是否漏项；不要用全仓正文扫描代替组件关系。
3. 先修改正式所有者，再同步入口与地图、引用方、Schema／示例、看板动作或快照、升级清单、发布选择规则以及面向人和 Agent 的文档。模板文件新增、删除、重命名或移动时，必须在形成正式提交前给每个变化路径明确标注“公开产品、私密排除或本地不入库”；未分类的新产品文件不能被发布候选静默省略。
4. 新组件登记稳定 ID、所有者、路径、依赖、投影和普通上下文策略；删除、移动或重命名必须清除旧链路。

### 实例正式资产与状态

1. 先确认唯一正式所有者和用户授权，再按“目标正文 → 实例领域地图／索引 → 必要信号投影 → 看板快照”更新。
2. 新增、激活或迁移正式记忆、能力、SOP 或经验后，必须证明存在一条 `asset_kind` 与正文 `kind` 一致、`target` 直接指向真实正文的路线。`task-family` 只是 `on-demand` 导航，不能代替正式资产路线。
3. 不为检查可达性把全部资产正文交给模型。先用地图和 frontmatter 做确定性闭包检查，只对命中的缺口读取少量正文。
4. 目录说明、派生投影或模板占位文件如果被旧实例引用为用户正文，必须先逐字节迁移并更新引用，验证成功后才能替换模板说明。

### 实例组件与本机依赖

1. 先由 `core/ownership.toml` 判断现有原生层能否完整拥有本次写集；可以时沿原所有者执行，只做兼容闭包，不复制登记。
2. 不能由原生资产或专业扩展表达的独立模块、能力适配器、本机工具适配器和集成适配器，使用 `instance/components/registry.toml` 与目标组件清单登记稳定所有权和接口。
3. 组件不得直接修改模板核心或另一个组件。旧实例已有直接核心修改时，只在隔离候选中转换为扩展点、适配器或版本化迁移；无法转换时保留并停止。
4. 设备本地路径只登记 `.assistant-local/**` 相对边界；外部绝对路径只留在声明的本机绑定文件。升级保留并复核绑定，不把它们复制进公开或迁移主体。

## 4. 每次正式修改的完成流程

1. **说明现象与根因**：区分用户可见故障、直接原因、根因和证据不足；不能把“改了一个文件”写成“问题已解决”。
2. **冻结边界**：列出原件、允许修改的候选、不可触碰内容、授权范围和回退点。对外部实例始终只改隔离副本。
3. **定义验收**：在动手前写清修复后用户能观察到什么、哪些数据必须保持、哪些引用／状态／入口必须一致，以及第二次执行应不再产生差异。
4. **实施最小充分修复**：修复根因和必要联动，不加入与本问题无关的框架、流程或演示数据。
5. **处理已有实例与分发路径**：可携带行为发生变化时，必须提供版本化迁移或明确冲突路径；不能只修空模板后假定旧实例自然恢复。引入实例兼容 Schema 时还要提供旧实例一次性纳管路线、空注册表和接口迁移说明，证明活跃未知内容不会被延后到日常使用时处理。模板文件集合变化时，同步目标版本发布清单、公开允许／拒绝集合、第三方声明和必要的安装／演示入口，再从固定提交验证完整文件分类；不能只在临时公开候选里补删文件。
6. **内部验证**：按 `RESULT_VALIDATION.md` 选择与风险相称的检查。文字核对来源和引用；TOML／Schema 做解析与最小反例；地图检查稳定 ID、类型、状态和真实目标；派生投影回查正式真源；升级和安全变化做隔离故障注入、回滚、资产保留与幂等检查。
7. **证明没有转嫁负担**：普通启动预算和渐进路由保持不变；必要检查由 Agent 在任务内安静完成，不要求普通用户理解内部字段、打开多个终端或手工跑回归。
8. **紧凑交付**：告诉用户实际修了什么、用什么证据验证、原件是否保持、还有哪些范围未验证。详细证据保存在任务报告，不把内部检查清单倾倒给普通用户。

只有最终状态为 `validated` 才能宣布正式变更完成。失败或证据不足时返回 `limited`／`failed` 和准确边界，不通过扩大测试、伪造成功或隐藏失败来追求“全绿”。

## 5. 多文件写入与损坏输入

只要一次正式动作会同时改变两个或更多耐久文件，就把它们视为一个动作级事务，而不是若干彼此独立的保存：

1. 写入前冻结本次允许修改的相对路径集合、各文件是否存在和原始字节摘要；已存在的原件保留到整组验证结束。
2. 先在同一文件系统的候选位置生成全部新内容并完成解析、引用、摘要和语义检查，再进入最终替换。深层 Windows 路径优先使用同目录、短名称临时文件，不能因临时后缀过长把原本合法的路径推过平台限制。
3. 最终替换必须覆盖整组允许路径。任一步失败或中断时，恢复整组旧状态；不能留下“一半新、一半旧”，也不能只回滚最后一个报错文件。
4. “文件不存在”和“文件存在但为空、截断、编码错误或无法解析”是两种状态。后者必须原样隔离或保留并停止覆盖，不能当成空模板、默认值或首次运行自动重建。
5. 只有新状态全部验证通过后才清除任务内备份／事务记录；相同输入第二次执行应不再产生差异。若中断跨会话，只投影一条极小恢复路线，不把写集、备份或验证正文放进普通启动。

这个事务基线是内部实现责任，不要求用户打开终端、逐文件批准或理解日志。单文件、可重建派生物可以使用更小的原子写入流程，但仍不能覆盖已知损坏的正式来源。

## 6. 触发与长期维护

新增或修改“达到某条件后做某事”的行为时，在 `core/maps/trigger-registry.toml` 登记类别、检查点、所有者、动态状态、启动策略、路线、门禁、清理和失败行为。除非出现现有事件族无法表达的全局触发，不把具体规则继续追加到启动入口。

任何检查系统本身也可能老化。长期治理 TODO 研究“怎样改进一致性体系”，不替代本协议；每次真实变更仍要当场完成联动和验证。
