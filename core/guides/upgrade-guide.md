# 模板升级指南

仅在用户明确要求检查或应用模板更新时读取。实例运行良好时不强制升级。

## 用户看到的简单流程

1. 用户直接说“帮我检查 Agent Carry 有没有官方新版本”，或在看板中复制升级请求；不需要自己寻找版本清单。
2. Agent 读取 `core/upgrade/official-source.toml`。允许联网时，只从其中登记的官方公开仓库和正式 Release 检查：先确定最新正式 Release 的版本标签，再取得这个标签对应的 GitHub 自动生成源码 ZIP。只有已经证明公开 `main` 与该标签指向同一提交时，才可改用登记的“最新版 ZIP”短链接。无法联网时，请用户提供已经下载到本地的升级包，不在搜索结果或镜像站中猜哪个是官方版本。
3. Agent 告诉用户当前版本、找到的目标版本和来源，只预览本次变化、个人内容保留方式与冲突，不立即升级。
4. 用户选择：保留现状，或迁移升级。
5. Agent 自动执行、验证并报告；用户不需要操作终端。

检查更新只在用户明确提出时进行。Agent Carry 不后台联网、不自动下载，也不会因为发现新版本就强制升级。公开仓库不需要 GitHub 登录；如果用户指定其他仓库、附件或镜像，Agent 必须明确说明它不是登记的官方来源，并在读取或下载前让用户决定。

## 预览

Agent 读取当前 `instance/manifest.toml`、`core/upgrade/official-source.toml`、目标发布清单和 `core/ownership.toml`，将文件分为：

- 模板核心：可按清单替换或迁移。
- 实例身份与个人资产：默认保留。
- 正在使用的扩展接口：检查兼容范围。
- 本地私密和派生文件：不从升级包覆盖。

专业实例如果存在 `workspace/<扩展 ID>/extension.toml`，Agent 只按这份清单区分“随实例保留的正文、可重建内容、当前电脑本地内容和隐私集合引用”，不会在普通启动或升级预览里打开整个专业工作区。存在工作区但没有合法清单时，Agent 会原样保留并把它列为需要判断的冲突，不会猜测、执行或删除。

实例如果存在 `instance/components/registry.toml`，Agent 只定向读取登记清单，核对稳定接口、便携正文和当前电脑本地绑定。兼容组件原样保留；可选不兼容组件停用但不删除；必需组件不兼容时保持旧实例并停止切换。旧实例第一次接入 1.4 协定时，在隔离候选一次性完成全部活跃资源分类和登记，不在日常调用时逐项迁移。

如果现有实例已经有 `.assistant-private/catalog.toml`、`bindings.toml` 或私密正文，预览必须把它们列为“实例本地私密状态，原样保留”；模板只替换公开 Schema 与空模板，不创建、重置或猜测当前设备绑定。旧实例没有目录文件不构成升级失败：只有以后登记资料、命中 `private_refs`、导入导出或完整迁移时，才从当前相关引用渐进建立。

如果用户改过模板核心，先在隔离候选按实例兼容协定判断能否转换为已有扩展点、组件适配器或版本化迁移；原件保持不动。确实无法安全表达时，明确提示“该实例存在尚不能兼容迁移的核心修改”，保留旧实例并给出具体冲突，不让用户面对逐行合并工具。

预览还要检查一个旧版兼容问题：有些早期实例把完整个人档案直接写在 `instance/profile/README.md`，并让 `profile.user_preferences_ref` 指向它；新模板又把同一路径当作目录说明。发现这种结构时，预览必须明确显示“先把个人档案原样迁到 `instance/profile/approved-profile.md` 并更新引用，再替换目录说明”，不能把 README 直接覆盖。目标文件已有不同内容时显示冲突并停止自动迁移。

## 两个选择

- **保留现状**：跳过本次升级，实例继续工作。
- **迁移升级**：导出实例身份、偏好、记忆、能力、SOP、经验、延期卡、跨会话正式状态、长期治理卡的实例排期状态、不含秘密的宿主档案和批准过的进化成果；从新模板创建干净实例；按 Schema 迁入并重建路由地图、唤醒胶囊、非启动时间索引和看板快照。发布清单 `replace_instance_guides` 中精确列出的实例目录 `README.md` 使用新模板说明，避免旧规则和重复索引永久残留；同目录的所有其他文件、用户子目录、除固定说明外的实例档案与本地私密层继续保留。长期治理卡按稳定 ID 使用新模板的正文、频率与步骤，同时保留实例自己的启停、锚点、上次完成、下次到期、延后和触发修订；缺失、重复或 ID 变化时作为冲突预览，不能重置成模板空态。旧核心改动不自动带入，除非用户把它明确认定为个人资产或扩展。宿主档案保留的是历史观察，升级后在相关能力使用时重新验证。

升级前先确认用户实际能找到的看板入口已经存在，再创建临时回滚副本。Agent 在隔离目录组装候选，验证整棵目录、用户内容和平台特有元数据后才切换；多文件动作中断时整组恢复，不留下半新半旧。Windows 上普通候选优先继承目标父目录权限，不默认复制系统审核权限或所有者，也不因失败擅自提权。目标模板从固定发布内容或可信提交的允许文件集合组装，不能把开发目录里的 `node_modules`、Git 元数据、缓存或维护者私密文件因广义通配符一起复制。

合并完成后，Agent 必须根据当前实例真实内容重新生成两份一致的看板快照，不能保留目标模板的空白演示数据。随后从稳定入口实际打开：快捷方式目标、工作目录、离线资源、匿名身份胶囊、页面标题和实例测试共同构成验收证据。能读取地址栏时再核对精确落点；工具暂时读不到地址栏，但其他独立证据全部一致，不会因此单独回滚一个有效实例。真正缺少入口、打开错误页、身份不一致或测试失败时仍会停止并恢复旧实例。

升级后还会检查入口、地图目标、资产风险／授权／成熟度字段、实例交流方式与学习政策、长期治理卡正文版本与实例排期字段、跨会话控制修订、触发注册表、唤醒胶囊与时间索引聚合、宿主接入协议／Schema、私密目录按需入口、看板动作、快照、扩展接口和实例方向锁定。所有任务族路线必须是 `on-demand`；所有已激活、试用或待复核的正式记忆／能力／SOP／经验必须有类型一致、直达真实正文的实例路线。上述闭包先由确定性工具读取地图和 frontmatter 完成，不把全部正文、扩展工作区或私密目录塞进模型。旧实例缺少 `profile.guidance_mode` 时按 `balanced` 兼容读取，只在用户调整交流方式或清单因其他正式变化被迁移时写入；不得借补字段改变锁定方向。旧资产缺少新字段、旧实例缺少私密目录或没有专业工作区时都按保守默认值读取，只在相关内容被使用、修改、导出或复核时渐进补齐。Agent 自动完成升级验收并把结果交给用户确认后，才删除本次升级创建且不属于失败证据的临时回滚副本；用户自行生成的备份包、明确要求保留的现场和失败证据不处理。

目录和静态检查通过后还不能直接说“升级完整完成”。如果产品文件是在当前运行开始后切换，本次会话原有接入回执只代表旧版本；按 `core/protocols/UPGRADE_SESSION_ACTIVATION.md` 在当前原子操作结束后的安全节点自动运行严格启动入口，核对同一实例、目标版本与 manifest 摘要，只加载最小新版入口和本次相关变化，检查不可变宿主规则冲突，再由 Agent 自动完成一项无破坏的代表行为验收。完整有界接续可以证明当前对话采用了可重载的新版产品规则，但不能冒充宿主改写了系统级指令链；普通文件重读、版本号、哈希、胶囊、快照和静态字符串仍不能单独证明采用。宿主确实阻止原地接续时，保留有效实例和当前可用能力，清楚报告文件升级与当前对话采用状态；不要求用户亲自测试，新任务只在用户希望立即使用受影响的新行为时作为最后兼容路线。会话待接续或单项行为验收失败不回滚有效实例，也不停止无关能力；只有切换后的文件或启动真源无效才按文件事务回滚。

从 1.2.1 升到 1.3.1 时还要完成四项定向迁移：为 frontmatter 与直接路线成对补齐保守确认门；把没有真实旧批准证据的 policy 授权资产留在复核；用现有真实结果建立 `instance/validations/index.toml`，旧成熟度无法闭合时进入“需要证据／复核”而不是补造记录；严格回读 manifest 后，在同一可恢复事务中重建 `instance/startup-capsule.toml` 并核对源摘要。风险分级只影响候选验证和复核顺序，不会在升级过程中自动采用正式资产。详细规则见 `core/upgrade/upgrade-1.2.1-to-1.3.1.md` 与 `core/upgrade/release-manifest-1.3.1.toml`。

从 1.3.0 升到 1.3.1 不重新执行上述旧资产迁移，只更新模板拥有的产品文件和实例产品版本，再重建启动胶囊与两份真实快照。1.3.1 修复发布 authority，并在继续禁止整个 `.assistant-local`／`.assistant-private` 的前提下，只允许发布清单逐字列出的九个普通零字节 `.gitkeep`。详细规则见 `core/upgrade/upgrade-1.3.0-to-1.3.1.md`；任何新的公开提交、标签、Release 或 Pages 仍需独立授权。

1.3.1 → 1.4.0 增加实例持续进化兼容协定、小型组件登记和旧实例一次性纳管；详细规则见 `core/upgrade/upgrade-1.3.1-to-1.4.0.md` 与 `core/upgrade/release-manifest-1.4.0.toml`。该历史发布保持不变。

1.4.0 → 1.4.1 修复首次实例化身份事务闭包：尚未实例化的 1.4.0 模板升级后仍保持空模板，并必须能够从同一真源完成通用和领域两条首次创建链；已经实例化的 1.4.0 只更新产品版本并重建严格启动胶囊与真实双快照，身份、方向、档案、资产、验证记录、候选、组件、专业扩展、工作区、本机绑定和私密状态继续保留。详细规则见 `core/upgrade/upgrade-1.4.0-to-1.4.1.md` 与 `core/upgrade/release-manifest-1.4.1.toml`。该历史发布保持不变。

1.4.1 → 1.4.2 只稳定实际使用回执、阶段学习回执和回复末尾的用户行动引导，不改变现有 Schema、组件接口、实例持续进化协定或首次实例化事务。空模板保持空白；已经实例化的 1.4.1 保留全部实例身份、档案、资产、验证、候选、组件、扩展、工作区、本机绑定和私密状态，只更新产品版本并重建严格启动胶囊与真实双快照。详细规则见 `core/upgrade/upgrade-1.4.1-to-1.4.2.md` 与 `core/upgrade/release-manifest-1.4.2.toml`。该历史发布保持不变。

1.4.2 → 1.4.3 修复文件切换后旧运行会话可能继续沿用旧指令链、却被误报为升级完整完成的问题。它把来源核对、文件安装、实例切换、会话激活和真实行为验收分开；有效实例在等待新任务激活或单项行为失败时继续可用，只隔离升级完成结论，只有目标文件或启动真源无效才回滚文件事务。它还要求最终用户行动回到总体目标中的下一项未完成工作。详细规则见 `core/upgrade/upgrade-1.4.2-to-1.4.3.md` 与 `core/upgrade/release-manifest-1.4.3.toml`。该历史发布保持不变。

1.4.3 → 1.4.4 加入按需 Skill 工坊：推荐不自动转换，只有用户明确选中的正式方法才在本地隔离副本中由 Agent 自动脱敏、通用化和参数化；别人分享的 Skill 先只读检查，不执行脚本、不安装依赖、不自动改写。单个包只会进入 `ready`、`review` 或 `isolated` 的局部结果，不影响 Agent Carry 主体。空模板继续为空；已有实例逐字节保留 SOP、能力、已安装 Skill、本地导出包和其他用户内容，升级本身不会生成、分享或安装 Skill。详细规则见 `core/upgrade/upgrade-1.4.3-to-1.4.4.md` 与 `core/upgrade/release-manifest-1.4.4.toml`。该历史发布保持不变。

当前官方正式目标是 1.4.5。1.4.4 → 1.4.5 修复长期对话中的升级连续性：每个新实质目标开始前只做一次极小 Agent Carry 启动基线比较；文件切换后，Agent 在当前原子操作结束的安全节点自动完成严格入口核对、最小新版规则接续、不可变宿主冲突检查和一项无破坏的代表行为验收，不把测试交给用户。普通文件重读不能冒充采用；宿主确实阻止原地接续时，只保持受影响行为待接续，有效实例和无关能力继续可用，新任务才是立即采用新版的最后兼容路线。空模板保持空白；已有实例的全部用户内容逐路径、逐字节保留。详细规则见 `core/upgrade/upgrade-1.4.4-to-1.4.5.md` 与 `core/upgrade/release-manifest-1.4.5.toml`。正式升级必须核对固定 `v1.4.5`、对应 Release、发布清单和解压树，并取得用户对该次升级的明确选择；这不授权任何未来提交、推送、标签、Release 或 Pages。

完整机器规则见 `core/upgrade/UPGRADE-CONTRACT.md` 和对应发布清单。GitHub 自动生成 ZIP 的外层目录名和压缩容器字节可能变化，因此升级验证以正式标签、发布清单、解压后的文件集合与逐文件内容为准，不把 ZIP 文件本身的一次 SHA-256 当作永久身份。升级包仍按不可信输入检查路径安全；这些来源与完整性检查会降低风险，但不向普通用户承诺“官方绝对安全”。
