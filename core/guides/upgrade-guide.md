# 模板升级指南

仅在用户明确要求检查或应用模板更新时读取。实例运行良好时不强制升级。

## 用户看到的简单流程

1. 用户直接说“帮我检查 Agent Carry 有没有官方新版本”，或在看板中复制升级请求；不需要自己寻找版本清单。
2. Agent 读取 `core/upgrade/official-source.toml`。允许联网时，只从其中登记的官方公开仓库和正式 Release 检查：先确定最新正式 Release 的版本标签，再取得这个标签对应的 GitHub 自动生成源码 ZIP。只有已经证明公开 `main` 与该标签指向同一提交时，才可改用登记的“最新版 ZIP”短链接。无法联网时，请用户提供已经下载到本地的升级包，不在搜索结果或镜像站中猜哪个是官方版本。
3. Agent 告诉用户当前版本、找到的目标版本和来源，只预览本次变化、个人内容保留方式与冲突，不立即升级。
4. 用户选择：保留现状，或迁移升级。
5. Agent 自动执行、验证并报告；用户不需要操作终端。

检查更新只在用户明确提出时进行。Agent Carry 不后台联网、不自动下载，也不会因为发现新版本就强制升级。公开仓库不需要 GitHub 登录；如果用户指定其他仓库、附件或镜像，Agent 必须明确说明它不是登记的官方来源，并在读取或下载前让用户决定。

## 预览

Agent 读取当前 `instance/manifest.toml`、`core/upgrade/official-source.toml`、目标发布清单和 `core/ownership.toml`，将文件分为：

- 模板核心：可按清单替换或迁移。
- 实例身份与个人资产：默认保留。
- 正在使用的扩展接口：检查兼容范围。
- 本地私密和派生文件：不从升级包覆盖。

专业实例如果存在 `workspace/<扩展 ID>/extension.toml`，Agent 只按这份清单区分“随实例保留的正文、可重建内容、当前电脑本地内容和隐私集合引用”，不会在普通启动或升级预览里打开整个专业工作区。存在工作区但没有合法清单时，Agent 会原样保留并把它列为需要判断的冲突，不会猜测、执行或删除。

如果现有实例已经有 `.assistant-private/catalog.toml`、`bindings.toml` 或私密正文，预览必须把它们列为“实例本地私密状态，原样保留”；模板只替换公开 Schema 与空模板，不创建、重置或猜测当前设备绑定。旧实例没有目录文件不构成升级失败：只有以后登记资料、命中 `private_refs`、导入导出或完整迁移时，才从当前相关引用渐进建立。

如果用户改过模板核心，明确提示“该实例存在个性化核心修改，默认更新可能无法直接应用”。不要让用户面对复杂合并工具。

预览还要检查一个旧版兼容问题：有些早期实例把完整个人档案直接写在 `instance/profile/README.md`，并让 `profile.user_preferences_ref` 指向它；新模板又把同一路径当作目录说明。发现这种结构时，预览必须明确显示“先把个人档案原样迁到 `instance/profile/approved-profile.md` 并更新引用，再替换目录说明”，不能把 README 直接覆盖。目标文件已有不同内容时显示冲突并停止自动迁移。

## 两个选择

- **保留现状**：跳过本次升级，实例继续工作。
- **迁移升级**：导出实例身份、偏好、记忆、能力、SOP、经验、延期卡、跨会话正式状态、长期治理卡的实例排期状态、不含秘密的宿主档案和批准过的进化成果；从新模板创建干净实例；按 Schema 迁入并重建路由地图、唤醒胶囊、非启动时间索引和看板快照。发布清单 `replace_instance_guides` 中精确列出的实例目录 `README.md` 使用新模板说明，避免旧规则和重复索引永久残留；同目录的所有其他文件、用户子目录、除固定说明外的实例档案与本地私密层继续保留。长期治理卡按稳定 ID 使用新模板的正文、频率与步骤，同时保留实例自己的启停、锚点、上次完成、下次到期、延后和触发修订；缺失、重复或 ID 变化时作为冲突预览，不能重置成模板空态。旧核心改动不自动带入，除非用户把它明确认定为个人资产或扩展。宿主档案保留的是历史观察，升级后在相关能力使用时重新验证。

升级前先确认用户实际能找到的看板入口已经存在，再创建临时回滚副本。Agent 在隔离目录组装候选，验证整棵目录、用户内容和平台特有元数据后才切换；多文件动作中断时整组恢复，不留下半新半旧。Windows 上普通候选优先继承目标父目录权限，不默认复制系统审核权限或所有者，也不因失败擅自提权。目标模板从固定发布内容或可信提交的允许文件集合组装，不能把开发目录里的 `node_modules`、Git 元数据、缓存或维护者私密文件因广义通配符一起复制。

合并完成后，Agent 必须根据当前实例真实内容重新生成两份一致的看板快照，不能保留目标模板的空白演示数据。随后从稳定入口实际打开：快捷方式目标、工作目录、离线资源、匿名身份胶囊、页面标题和实例测试共同构成验收证据。能读取地址栏时再核对精确落点；工具暂时读不到地址栏，但其他独立证据全部一致，不会因此单独回滚一个有效实例。真正缺少入口、打开错误页、身份不一致或测试失败时仍会停止并恢复旧实例。

升级后还会检查入口、地图目标、资产风险／授权／成熟度字段、实例交流方式与学习政策、长期治理卡正文版本与实例排期字段、跨会话控制修订、触发注册表、唤醒胶囊与时间索引聚合、宿主接入协议／Schema、私密目录按需入口、看板动作、快照、扩展接口和实例方向锁定。所有任务族路线必须是 `on-demand`；所有已激活、试用或待复核的正式记忆／能力／SOP／经验必须有类型一致、直达真实正文的实例路线。上述闭包先由确定性工具读取地图和 frontmatter 完成，不把全部正文、扩展工作区或私密目录塞进模型。旧实例缺少 `profile.guidance_mode` 时按 `balanced` 兼容读取，只在用户调整交流方式或清单因其他正式变化被迁移时写入；不得借补字段改变锁定方向。旧资产缺少新字段、旧实例缺少私密目录或没有专业工作区时都按保守默认值读取，只在相关内容被使用、修改、导出或复核时渐进补齐。用户验收后自动删除本次升级创建的临时回滚副本；用户自行生成的备份包和明确要求保留的失败现场不处理。

从 1.2.1 升到 1.3.0 时还要完成四项定向迁移：为 frontmatter 与直接路线成对补齐保守确认门；把没有真实旧批准证据的 policy 授权资产留在复核；用现有真实结果建立 `instance/validations/index.toml`，旧成熟度无法闭合时进入“需要证据／复核”而不是补造记录；严格回读 manifest 后，在同一可恢复事务中重建 `instance/startup-capsule.toml` 并核对源摘要。风险分级只影响候选验证和复核顺序，不会在升级过程中自动采用正式资产。详细规则见 `core/upgrade/upgrade-1.2.1-to-1.3.0.md` 与 1.3.0 发布清单。

完整机器规则见 `core/upgrade/UPGRADE-CONTRACT.md` 和对应发布清单。GitHub 自动生成 ZIP 的外层目录名和压缩容器字节可能变化，因此升级验证以正式标签、发布清单、解压后的文件集合与逐文件内容为准，不把 ZIP 文件本身的一次 SHA-256 当作永久身份。升级包仍按不可信输入检查路径安全；这些来源与完整性检查会降低风险，但不向普通用户承诺“官方绝对安全”。
