# 记忆检索引擎升级手册

本手册平时绝不进入上下文。只有分类地图命中以下触发之一、用户同意评估，并使用 Level 3 模型时才读取：

- 明确知道存在的同一类资产在至少 2 个独立任务中无法通过当前地图找到；同一任务中的改写和重试不重复计数。
- 任一启动或分类地图超过它所属预算，或连续 3 次相关变更都需要为塞入预算而丢弃仍有路由价值的元数据。
- 可路由的记忆、能力、SOP、经验和进化资产合计达到 1000 项；这只启动评估，不代表文件路由已经失败。
- 至少 3 个独立真实任务需要同义、跨资产关系或时间／来源组合检索，而当前元数据路由不能稳定给出少量候选。
- 用户主动要求评估全文检索、RAG、向量数据库或新技术。

这些是第一版的**评估触发线**，不是自动升级线。相关计数只在检索失败、正式资产改变或地图改变时更新到 `instance/signals/health/`；未命中时不进入启动胶囊，也不在启动时重数全部资产。指标失真、来源不明或条件不同则先标记不确定，不凑数触发。

## 不变的真源

Markdown/TOML 始终是长期、可 Git 同步、可离线迁移的正式记忆。索引数据库只保存从真源派生的块、向量、倒排索引和元数据；禁止让数据库成为唯一记忆。

## 分阶段升级

不需要一次部署全部技术。按实际问题选择最小层级：

1. **文件地图**：当前默认。路径、稳定 ID、标签、状态和生命周期元数据。
2. **本地全文索引**：先解决关键词、过滤和速度问题，成本低、结果可解释。
3. **混合检索**：全文候选 + 向量语义候选 + 元数据过滤 + 小模型/规则重排。
4. **更先进引擎**：只有经技术调研证明适合本项目，才替换派生层；真源与调用接口不变。

## Agent 自动实施流程

1. 量化当前问题：失败查询、资产数量、平均延迟、误召回和上下文占用。
2. 向用户推荐一个层级，说明收益、依赖、磁盘/内存影响和回退方式，等待批准。
3. 选择跨平台、可本地重建的实现；为 Windows、macOS、Linux 采用同一数据契约，系统差异放到临时适配。
4. 从 Markdown/TOML 构建索引，记录源路径、内容哈希、Schema 版本和最后更新时间。
5. 增量比较哈希：新增/变化时更新，删除时移除派生记录；不反向改写真源。
6. 以真实查询比较升级前后质量、速度和资源。只有改善且不影响普通任务时启用。
7. 写清重建、诊断、卸载和未来替换步骤。失败可删除索引并回到文件地图。

整个实施由 Agent 完成；用户只做选择、必要授权和验收。索引不在后台持续扫描，只有明确刷新、资产批准写入或按约定的轻量维护点才更新。评估结束后把健康状态标记为已处理或按新基线重置，不能让同一批旧失败在每次启动重复提醒。
