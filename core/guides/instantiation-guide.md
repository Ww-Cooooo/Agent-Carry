# 实例化引导

仅当清单状态为 `template`，且安装完成后需要进入首次创建，或用户明确要求开始实例化时读取。`first-run-guidance` 负责解释入口、说明三种引导路线和收集用户的第一批选择，不要求当前模型先具备 Level 3；任何完成安装的宿主 Agent 都必须把用户带到这里。`instantiation` 负责渐进访谈、实例结构设计、写入前完整预览、正式写入和方向锁定，仍属于 Level 3 工作；该路线先读取 `core/guides/first-use-execution-gates.md`，再按其中要求读取本指南和回到临门检查点。当前模型不足时，先完成下面的首次引导并保留用户已经给出的信息，再在进入正式访谈和结构设计前按模型等级协议请求切换；不得把“需要 Level 3”当成安装后不引导用户的理由。

## 安装成功后的第一条回复（强制）

当安装结果为完整完成，或虽为有限完成但空白模板仍可使用，且 `instance/manifest.toml` 仍是 `state = "template"` 时，安装与首次创建属于同一段连续的用户体验。安装 Agent 不得用“已完整完成安装”、路径清单、版本号或安全动作清单作为主要回复后结束，也不得只问一句没有解释的“你希望怎样交流”。安装失败且模板不可用时先如实报告阻塞，不套用成功欢迎词。

完成入口验证后：

1. 当前宿主能够打开用户可见窗口时，从已经验证的桌面或系统等价入口打开看板，并让页面停留在总览；只做无界面的自动检查不等于已经把看板呈现给用户。无法可靠打开可见窗口时，如实给出入口位置，但不能因此停止聊天引导。
2. 第一条面向用户的回复必须先邀请用户创建自己的助手，再同时给出两个等价入口：在看板首页右侧的“第一次使用”卡片点击“创建我的助手”，或直接在当前聊天中继续。看板不会直接改写模板：用户在弹窗中完成选择后，要在第三步点击“生成创建指令”，再把完整指令交回当前 Agent／聊天。不得假设用户一定会看见、理解或操作看板。
3. 同一条回复必须完整解释三种引导路线分别适合什么情况、当前 Agent 会怎样配合，并只让用户回答这一个问题。用户可以回复 `1`、`2`、`3`，也可以直接描述自己的情况，让 Agent 推荐；不能只列“一步步引导／适度引导／直接协作”三个名称。
4. 整体安装状态、来源、安装位置、入口、实际打开结果、模板状态和未执行的高影响动作仍要如实记录，但放在引导之后，写成一个简短而信息完整的安装摘要；不得为了压缩字数遗漏必填事实，也不得让技术回执成为对话终点。

这些要求不能只在安装开始时读一次。入口验证结束、准备发送第一条回复时，必须重新打开 `core/guides/first-use-execution-gates.md` 的“A. 安装完成后的回复门”，逐项满足退出条件后再回复。

弱模型可以直接使用下面的回复。方括号内容必须根据真实结果替换；无法证明看板已经在用户可见窗口中打开时，使用“看板入口在……”而不是声称“我已经打开”：

> 接下来，我带你把这份空白模板创建成真正属于你的 Agent Carry 助手。
>
> 我已经为你打开 Agent Carry 看板。你可以在首页右侧的“第一次使用”卡片点击“创建我的助手”，完成前两步选择，在第三步点击“生成创建指令”，再把生成的完整内容交回当前 Agent，也就是发到现在这个聊天里。我会继续了解你的真实需求，给你看一份完整预览，得到你明确确认后才会正式创建。如果你没有看见、不想操作看板或暂时打不开，也可以直接在这里继续；两个入口会进入同一套创建流程。
>
> 先告诉我你更接近哪种情况，只回复 `1`、`2`、`3` 就可以：
>
> 1. **第一次接触 Agent**：不懂编程或提示词也没关系。我会使用你当前选择的交流语言，从你的职业、眼前困难和想完成的事情开始，一次只问一个容易回答的问题。
> 2. **已经用过一些**：你能说出大致需求，或者懂一点 Agent／编程。我会保留必要解释，只补问真正会影响助手设计和结果的关键信息。
> 3. **经常使用 Agent**：你熟悉 Agent、编程或自己的专业工作流。我们可以直接讨论资料、标准、工具、SOP、自动化边界和验收方式，更快进入设计。
>
> 如果你不知道该选哪个，直接告诉我你的职业、目前最困扰或最耗时间的事情，以及你希望 AI 帮你完成什么，我会先推荐适合的方式，再继续带你创建。
>
> 安装摘要：整体状态是 `[完整完成或有限完成]`；来源是 `[GitHub 链接或完整压缩包]`；Agent Carry 位于 `[实际安装位置]`；看板入口名称是 `[实际名称]`，位于 `[实际位置]`；从该入口实际打开的结果是 `[真实结果]`。当前仍是安全的空白模板；在完成渐进访谈、看过完整预览并得到你的明确确认前，不会写入或锁定助手方向。安装过程 `[如实列出没有执行的高影响动作，例如：没有创建或推送 GitHub 仓库，也没有读取或上传秘密凭据]`。

如果看板没有在用户可见窗口中打开，第二段替换为：

> Agent Carry 看板入口名称是 `[实际名称]`，位于 `[实际位置]`。打开后，请在首页右侧的“第一次使用”卡片点击“创建我的助手”，完成前两步选择，在第三步点击“生成创建指令”，再把生成的完整内容交回当前 Agent，也就是发到现在这个聊天里。如果你暂时不想打开或打不开，也可以直接在这里继续；两个入口会进入同一套创建流程。

用户回答后，先确认对应交流方式只是可随时调整的引导节奏，再继续询问助手方向：

- **通用个人助手**：适合任务跨多个领域，或用户现在还没有明确的专业培养目标；它会在长期使用中逐渐熟悉通用偏好、习惯和工作方式。
- **具体领域的专业助手**：适合围绕一个职业、行业或专业方向长期积累任务地图、判断标准、能力和固定流程。
- **先帮我判断**：用户可以只说职业、困难和目标，由当前 Agent 比较前两种方向并提出建议；它不是第三种正式方向，用户最终仍须确认 `general` 或 `domain`。

用户不点击看板、直接说出职业、困难、目标或专业要求时，视为选择了聊天入口。Agent 应利用这些信息推荐引导方式并继续访谈，不得要求用户返回看板重新填写，也不得因用户没有使用界面而中止。看板已经附带合法选择时则直接沿用，不重复询问。

以下回复均不合格：

- 只报告安装位置、版本、提交、快捷方式和安全边界，然后结束；
- 只问“每一步都解释、只补充关键点，还是直接协作”，却不说明三种路线适合谁、接下来会发生什么；
- 只让用户自己去看板寻找入口，不提供聊天中的完整备用路线；
- 只在聊天中列出选项，却不说明看板已经打开或入口在哪里；
- 用户说“不知道”时继续逼用户分类，而不是根据职业、困难和目标帮助判断；
- 当前模型不足以正式实例化时，在解释入口和收集第一项选择之前就停止工作。

## 两个互不替代的选择

实例化开始时依次确认两个维度，不把它们合并成六套固定问卷，也不把用户贴上永久等级标签。

### 1. 交流方式

先让用户选择当前更舒服的协作方式：

- `step-by-step`（第一次接触 Agent）：使用用户当前交流语言逐步解释，从用户真实工作出发，每次只问一个容易回答的问题。
- `balanced`（已经用过一些）：默认用户能说出大致需求，只补问会影响结果的关键信息，并在关键决定处解释原因。
- `direct`（经常使用 Agent）：允许直接讨论标准、资料、工具、SOP、自动化边界和验收方式，减少基础解释。

这只是可随时调整的沟通偏好，不是用户能力评分，也不对应模型 Level 1／2／3。一个专业领域里的专家也可能第一次接触 Agent；一个熟悉编程的人也可以选择一步步讲解。三种交流方式都能创建通用助手或专业领域助手。

### 2. 助手方向

再问用户：

> 你想创建“通用个人助手”，还是“某个具体领域的专业助手”？如果现在还拿不准，我可以先了解你的工作和困难，再帮你比较；在你明确选择前不会锁定方向。

- `general`：方向是跨领域的个人工作支持，重点保存通用偏好、习惯、协作方式、跨领域 SOP 和可迁移能力。
- `domain`：方向锁定一个明确领域，重点构建该领域的任务地图、术语、质量标准、风险边界和专业工作流。
- “先帮我判断”只是实例化前的引导过程，不是第三种正式方向。了解情况后仍须由用户在 `general` 和 `domain` 中明确选择。

助手方向确认并实例化后永久锁定；交流方式可以在以后单独修改。若一个通用实例在长期使用后需要变成专业领域助手，应从干净模板创建新的领域实例，并可按偏好复用协议带入已经确认的通用沟通偏好；不得直接改写原实例的锁定方向。

## 按交流方式调整访谈

三种方式共用下面的渐进访谈和同一份写入契约，只改变提问顺序、解释密度与协作节奏：

- `step-by-step`：先问职业或主要工作、眼前困难和想完成的结果；使用用户当前交流语言复述，再给出少量真实任务候选。不要先讲提示词工程、目录、Schema 或内部架构。
- `balanced`：先了解用户已经怎样使用 Agent、最常处理的任务、常用资料或工具和希望改善的结果；已有答案不重问，只补足会改变方向、边界或首个任务的内容。
- `direct`：允许用户直接提供专业标准、样例、资料、工作流、SOP、工具、自治边界和验收条件；信息足够时快速进入预览，不强制经历入门问题。

看板里选择的交流方式和方向意向是用户本次明确输入。Agent 可以围绕真实需求继续追问，但不得要求用户重新点击或重复回答同一个选择。用户选择“先帮我判断”时，Agent 必须完成比较并再次取得正式方向选择，不能代替用户锁定。

用户选中或基本确定第一项真实任务后、准备索取当天金额、真实文件或其他实际任务输入前，必须重新打开 `core/guides/first-use-execution-gates.md` 的“B. 首项任务开始前的实例化交接门”。模板态只讨论候选任务的目标、材料类别和人工判断边界；先取得正式方向，等待用户明确确认当前模型处于 Level 3，完成下面的预览、写入和回读，再询问是否立即开始。不能用“先做一次任务试试看”跳过实例化，也不能让弱模型在没有 Level 3 明确确认时继续结构设计。

## 第一次接触 Agent 时

当 `guidance_mode=step-by-step`，或用户表示不知道 AI 能为当前职业做什么、只能说出眼前困境时，先使用用户当前交流语言围绕三件事逐步询问；用户已经说过的内容不要重复问：

1. 你从事什么职业，或现在主要负责什么事情；
2. 当前最困扰、最耗时间或最容易出错的事情是什么；
3. 你想完成什么结果，但不知道 AI 可以怎样帮忙。

取得最小充分信息后：

1. 先用用户听得懂的话复述对职业、困难和目标的理解，让用户能立即纠正；
2. 提出 2～4 个来自用户真实工作的候选任务，每个只说明“可以得到什么结果、需要用户提供什么、哪些判断仍由用户决定”，不展示内部能力清单；
3. 说明其中哪一项最适合作为第一次尝试以及原因，但最终由用户选择，也允许用户改写候选；
4. 把选中的一项写进实例化预览的“第一项真实任务”和对应初始任务族，不为了引导而预先制造记忆、能力或 SOP；初始任务族只登记为 `asset_kind = "task-family"` 的按需路线，目标指向真实存在的实例说明文件，不计入看板资产；此时不索取当天金额、真实业务文件等执行输入；
5. 实例化完成后，用一句自然语言询问是否立即开始这项任务。用户选择暂不开始时，只保留它作为明确的下一步，不自动变成待办。

如果需要联网了解某个职业的常见工作，只在确实能改善候选任务时加载外部安全边界并做有界调研；公开资料只能帮助提出候选，不能替用户定义职业、困难或最终方向。用户已经能清楚说明领域标准、资料和工作流时，即使当前选择了逐步引导，也应尊重已有信息、跳过重复问题；“逐步”不等于拖慢或低估用户。

## 逐步访谈

使用 `/grill-me` 思路逐分支提问，每次只问能改变设计的少量问题。用户可能遗漏需求，因此不要把初次回答当成永久封闭的功能清单。

至少覆盖：

1. **目标与成功**：希望助手替代或辅助哪些工作；什么结果才算好。
2. **典型任务**：高频、低频但重要、季节性/周期性和突发任务。低频不等于应删除。
3. **输入与输出**：常见文件、网站、软件、硬件、数据来源、成品格式。
4. **判断标准**：质量、风格、准确性、速度、成本和必须人工判断的部分。
5. **自动化边界**：哪些可直接做，哪些只需异常确认，哪些必须每次确认。
6. **隐私与外发**：默认把用户当前选择的宿主模型／API视为当前任务的执行环境，任务所需的隐私内容可以按需提供，不为同一任务逐项重复确认；额外网站、邮件、MCP／插件、其他 Agent／账号／人员和仓库属于新的接收方。API 密钥、密码、令牌、Cookie、私钥和恢复码不得进入模型上下文，优先由宿主凭据机制直接使用；所有 Git 副本默认排除隐私与秘密。用户只需在希望改成更严格的本地模型或逐项确认模式时另行选择。
7. **环境**：系统、Agent、模型接入、常用目录和可能换机后变化的路径。
8. **个人偏好**：沟通风格、解释深度、工作节奏、命名、格式和已有实例偏好是否复用。
9. **未来变化**：本方向内可能新增的需求、第三方工具改版、模型变化和生命周期。
10. **边界反例**：哪些看似相关但实际不属于本实例；越界时如何提示创建新实例。
11. **学习方式**：默认采用“Agent 在真实任务的自然停点主动说明发现的习惯、方法或纠正；用户只确认内容和适用范围，不需要说资产类型。风险分级只让证据充分的低风险候选更早进入复核；无论风险高低，用户明确选择采用或限定试用后，内容才进入正式资产”。用普通语言说明一次即可；用户可改为所有候选都只在主动提出时复核。

如果用户不了解该领域，按上面的第一次接触路径先从职业、困难和目标形成候选任务；必要时再根据公开资料和专业知识补充候选任务族，联网前加载外部安全边界。候选不是替用户决定，最终范围和第一项真实任务都由用户确认。

## 写入前预览

向用户展示：交流方式、方向类型、方向名称、范围声明、明确边界、初始任务族、第一项真实任务、自动化/确认策略、隐私策略、学习政策、环境假设和仍未知的内容。第一项真实任务必须来自用户已经说明的职业、困难、目标或专业工作，不得用模板示例替代。隐私策略默认说明“当前选定模型可处理任务所需隐私，但秘密凭据不进入模型；额外接收方另行判断；Git 不保存隐私与秘密”。学习政策要说明“用户不必主动说形成记忆或 SOP；Agent 发现可复用习惯和方法后会在自然停点使用用户当前交流语言询问。直接要求记住时也会集中展示一次精确预览，让用户选择怎样处理，完成这一次选择后不重复确认同一内容；询问前的一次推断只在当前任务中观察，选择先观察后才持久保存候选并允许以后累计验证证据，选择不保存或没有回应时不会留下候选、信号或提醒；风险分级政策只决定这类已获准观察候选的验证和复核优先级，任何候选变成正式资产前仍须用户明确确认具体内容和适用范围；身份、隐私、安全、重要偏好和高影响流程还要完整说明风险”。用户可补充、修正，或为隐私选择更严格模式、为学习选择 `manual-only`。

用户确认完整预览后，先重新打开 `core/guides/first-use-execution-gates.md` 的“C. 实例化写入门”，再一次性写入：

- `instance/manifest.toml`
- `instance/startup-capsule.toml`：从本次写入后的严格 manifest 在模型上下文外生成；只含 Schema 白名单字段和准确清单摘要，不复制档案正文、学习规则、验证索引或资产内容
- `instance/profile/approved-profile.md`：保存本次确认的实际实例档案和第一项真实任务；`instance/profile/README.md` 只保留模板目录说明，不写入用户正文
- `instance/maps/domain-map.toml`：根身份使用确定性值；`map_id="instance-domain"`、`instance_id` 等于新实例清单，通用实例写 `direction="general"`，领域实例写经过确认的 `direction.domain_id`，两类正式实例都写 `status="active"`。不得把显示名称、中文标签或模型临时概括写入 direction
- `instance/signals/control.toml`、`instance/maps/signal-map.toml` 与 `instance/maps/time-trigger-map.toml` 中的实例 ID
- `instance/evolution/index.toml`：写入同一实例 ID、`state = "empty"`、`source_revision = 0`，`generated_at` 使用本次真实实例化时间，保持 0 计数和正式预算；不得枚举候选正文，也不得继承模板或其他实例的候选

候选索引属于可重建派生物，但实例化事务必须给它写入新实例身份并保持干净空态，同时在 `versions.evolution_candidate_index_schema` 记录 `1.0`。空态必须回读 `generated_at` 为本次真实实例化时间、`candidate_count=0`、`indexed_count=0`、`active_count=0`、`budget_bytes=32768`、`overflow=false` 且没有 `[[candidates]]`；清单、索引与信号控制记录的实例 ID 必须在同一事务回读一致。任何一项仍为 `template`、沿用旧实例 ID、使用空时间、计数不一致或含候选条目时，实例化失败并回滚。相同空态第二次执行必须逐字节不变。

结果验证索引是实例拥有的正式低敏真源，不是可以因“目前没有资产”而省略的可选快照输入。实例化只初始化身份，不制造证据：必须回读 `instance_id` 与 manifest 一致、`state=empty`、`source_revision=0`、`generated_at=""`、`budget_bytes=262144`、`overflow=false`、`record_count=0` 且没有 `[[validations]]`。创建预览、方向锁定、胶囊有效或快照生成成功都不是第一项真实任务的结果验证。任何字段仍是模板、出现记录或计数不一致时整组回滚；相同输入第二次执行必须逐字节不变。

组件注册表也属于实例身份闭包。全新模板没有旧实例未知内容，不运行旧实例的一次性纳管流程；只在隔离候选中有界确认组件区恰好包含物理普通文件 `README.md` 与 `registry.toml`，没有其他文件、目录、链接或重解析点，再写入同一实例 ID 与 `adoption_state=current`。模板注册表的 revision 为 0；身份与纳管状态首次成为正式内容后递增为 1，保持 0 条目。若注册表只存在实例 ID、计数、状态、顺序或规范文本漂移，且目录事实仍严格证明为零组件，则先冻结原字节，在同一隔离事务按严格 manifest 与零目录事实确定性重建、回读并自然语言报告，然后继续实例化；不额外要求用户确认内部修复。若实际目录已出现未知组件内容、链接、无法证明为空的损坏清单或非零条目，就不再是干净首次实例化输入：保留原字节，只隔离创建事务并给出修复入口，不能用空注册表覆盖、猜测所有权或让 Agent 其他能力一起停止。

新实例的普通动态信号从干净空态开始。对模板自带且状态为 `active` 的长期治理卡，在实例化事务中以实际实例化时间作为 `schedule_anchor_at`，计算第一轮 `next_due_at = anchor + frequency_days`，再重建非启动时间索引；启动胶囊仍只写最早时间和总数，不写三张治理卡。用户明确暂停某项治理时不把它计入有效日程。公开模板中的维护者实际日期不得直接继承到新实例。

把 `direction.locked` 设为 `true`。以后可以在同一方向内新增任务、能力和 SOP，但不得把领域实例改成其他领域，也不得把通用实例改成领域实例；需要另一方向时从模板创建新实例。`profile.guidance_mode` 不属于方向锁，可以根据用户明确要求在 `step-by-step`、`balanced` 与 `direct` 之间修改。修改时只更新该字段和派生快照，不能借机重做实例化、改变方向或改写既有资产。
