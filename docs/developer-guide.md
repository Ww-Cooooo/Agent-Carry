# 开发者定制指南

Agent Carry 的默认体验面向普通用户；开发者可以在不破坏升级通道的前提下扩展。

## 优先使用扩展点

- 新的实例资产放入 `instance/` 对应目录并登记实例地图。
- 平台适配和本地工具保持可删除、可重建，不让其成为正式记忆真源。
- 安装入口由根目录 `INSTALL.md` 正式拥有；`START-HERE.txt` 只能引导到它。修改下载、解压、安装位置、桌面入口或首次设置衔接时，必须同时验证链接和压缩包两种来源，不能维护两套规则。
- 看板扩展遵循动作与快照 Schema；界面不能直接修改正式资产。
- 看板的信息架构、视觉、离线构建、电脑窗口适配和验收要求见 [看板设计与前端架构](dashboard-design.md)；新增界面不能绕过其中的数据与动作边界。
- 修改看板字体或 npm 运行依赖时，必须同步字体清单／OFL 或重新生成生产依赖声明，并让正式离线构建通过本地资源校验；不能只在开发机安装字体、从 CDN 引入资源或把 `node_modules` 当作最终用户依赖。
- 复制或改写 UI 模板、代码片段、图标、图片、模型、数据集等第三方内容时，先按 [开源合规与第三方来源](open-source-compliance.md) 固定官方来源、许可证、版权、修改关系与摘要。`npm run check:compliance` 拒绝未审核许可证和未登记二进制素材，不能通过扩大允许集合来掩盖未知来源。
- Agent Carry 自身采用 Apache License 2.0。发布候选必须保留根 `LICENSE`；第三方依赖、改写源码、字体和上游材料仍保留各自许可，并同步维护 `THIRD_PARTY_NOTICES.md`。不能用项目许可证覆盖第三方许可证，也不能在未确认公开版权主体名称时擅自写入维护者个人身份。
- 修改模板核心前先读取组件地图与变更协议，理解将来模板升级可能发生冲突。
- 修改官方仓库、Release 下载地址或升级入口时，以 `core/upgrade/official-source.toml` 为唯一公开更新来源记录，并同步升级指南、看板动作和 README；不能让 Agent 通过搜索结果或镜像猜测官方版本。
- 项目根的 `.agents/`、`.claude/` 与 `skills-lock.json` 只属于维护者本地 Agent／Skill 工具链，不是 Agent Carry 的运行时、安装材料或可携带资产。正式分发不能依赖这些目录；Git 安全候选也必须排除它们。需要复现前端或维护流程时，应由贡献者在自己的环境中另行安装相应工具。

## 同步架构文档

- 整体目标、参与者职责、跨 Agent 语义或正式资产关系发生变化时，同步更新 [架构与设计原则](architecture.md)。
- 涉及时间、次数、风险、健康、状态、版本、跨会话累计、运行投影或渐进展开时，同步检查 [统一触发治理与跨会话信号设计](cross-session-signal-map.md)。
- 修改跨会话运行行为时，以 `core/protocols/CROSS_SESSION_SIGNALS.md` 为执行真源，以 `core/schemas/cross-session-signal.schema.md` 为结构真源；设计说明不能代替二者。
- 修改跨宿主接入、能力发现、宿主协作记忆、任务胶囊或回传来源时，以 `HOST_SESSION_RESUME.md` 和 `HOST_INTEGRATION.md` 分别作为轻量恢复与完整接入的执行真源，以 `core/schemas/host-integration.schema.md` 为结构真源，并同步检查安全边界和 `instance/hosts/` 的按需加载约束。
- 修改记忆学习、候选匹配、风险分级、试用晋升、成熟度、证据压缩或宿主执行经验时，以 `core/protocols/ASSET_LIFECYCLE.md` 为执行真源、`core/schemas/asset-frontmatter.schema.md` 为结构真源，并同步检查 [资产学习、能力进化与 SOP 成熟](asset-evolution.md)、触发注册表、宿主回传和看板快照兼容投影。
- 修改来源约束交付、正式多文件验收、学习证据资格或任务内修正口径时，以 `core/protocols/RESULT_VALIDATION.md` 为执行真源，并同步检查 [任务结果验证说明](result-validation.md)、资产生命周期、任务交接 SOP、组件变更协议、触发注册表和升级清单。不要按宿主复制验证规则。
- 讨论确认但尚未实现的内容必须标为“已确认设计”或“待落地”，不能写成当前能力。
- 实现完成后同时更新架构文档的状态对照、对应正式协议、组件地图和必要的升级说明。
- 架构文档解释各部分为什么存在以及如何协作；具体可执行规则仍由 `core/protocols/`、`core/guides/` 和 Schema 拥有，避免出现两个互相漂移的正式真源。
- `core/maps/trigger-registry.toml` 是触发规则盘点真源，但普通启动不读取。新增规则必须先归类并声明检查点、状态、投影、门禁、清理与失败行为；不能逐条扩写启动入口。
- 唤醒胶囊和非启动时间索引都是可重建投影，不得成为正式资产真源、无限事件日志或普通任务必读的第四层。
- 宿主注册表和档案属于按需实例元数据，不得加入普通启动扫描；任何宿主专用适配只能引用它们，不能反过来拥有可携带资产语义。
- 当前执行模型、额外接收方、秘密凭据和 GitHub 私密备份的正式边界由 `EXTERNAL_CONTENT_SAFETY_BOUNDARY.md`、`HOST_INTEGRATION.md` 与 `PRIVACY_IMPORT_EXPORT_SOP.md` 共同投影。修改任一处时同步检查实例清单隐私模式、手动接入提示词、`.gitignore`、看板三项备份／导出／导入动作和公开发布 SOP。
- `.gitignore` 只能阻止尚未跟踪且命中路径规则的文件，不能发现普通 Markdown／TOML／源码中的误粘密钥，也不能自动移除已经跟踪的秘密。任何 Git 候选副本都必须对准确候选集合做路径与内容检查；报告只显示脱敏类别和位置，不回显秘密原值。
- `.gitignore` 中对本地 Agent／Skill 工具目录的排除只说明它们不属于产品候选，不能代替允许集合。生成公开候选或 GitHub 私密备份候选时，仍从正式组件清单重建允许集合，不能把某个维护者环境的 Skill、插件缓存或锁文件当作终端用户依赖。
- 能力与 SOP 正文拥有可携带语义；宿主执行经验只能按稳定 ID 指向核心并在相关任务使用时加载，不能复制或覆盖核心。
- 不把个人实例数据、临时任务包、本地验收记录或维护者私密流程写入公开架构文档。

## 验证强度

个人项目采用风险对应验证，而非默认企业级回归：

- 文案和链接：目标存在、语义一致。
- TOML/Schema：可解析、必填字段和关键约束。
- 安装：在隔离副本中验证完整包识别、冲突分支、桌面入口目标、离线打开和未授权动作清单；不要求普通用户运行开发依赖或全量回归。
- 看板：离线打开、快照错误降级、关键动作复制文本。
- 许可证：根 `LICENSE` 为完整 Apache License 2.0，产品、核心、发布清单和看板包元数据使用同一 SPDX 标识；第三方声明、改写源码映射、字体来源和随包许可证仍完整，`npm run check:licenses` 与 `npm run check:compliance` 均通过。
- 升级/隐私/安全：针对高风险路径做少量真实场景。
- 来源／契约约束结果：用新的阅读轮次比较原始依据与最终产物；同时做必要的解析、稳定 ID、引用、计数、投影和允许范围检查。只有 `validated` 可计学习成功；`limited` 必须暴露边界。

模型可以 3～5 次有根据地自我修正，其中结果验证默认占 1～2 轮聚焦修正；不能为了“通过测试”改掉被冻结的产品语义，也不能把同一事件内的修正重复计为成功证据。
