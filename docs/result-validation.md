# 任务结果验证说明

Agent Carry 不把“模型写完了”直接等同于“结果可靠”。真实宿主测试表明，不同模型都会在第一次交付中偶尔把常见经验补成来源事实，或在跨文件更新后漏掉一个引用；模型自己的第一轮自检也可能过早判断成功。

解决办法不是给每个宿主写一套规则，也不是让普通用户运行大型回归。Agent Carry 使用一扇按需出现的轻量结果验证门：只有来源／契约约束的产物、正式多文件变更、高影响任务，或准备成为学习证据的结果，才在交付前做一次新的阅读与核对。

## 它怎样工作

1. **先形成产物**：当前模型和宿主按任务要求完成工作。
2. **只组合小型依据**：重新读取用户目标、本次真正使用的来源或契约、最终产物和紧凑验收标准，不加载整段聊天或整个资产库。
3. **检查来源主张**：区分来源事实、Agent Carry 正式政策、明确标注的通用解释和未知项，防止按钮、路径、版本、覆盖、合并、删除、秘密配置等细节被常识补写。
4. **检查结构关系**：只在相关时解析文件、核对稳定 ID、目标引用、计数、时间、投影、冻结边界和真实可观察结果。
5. **聚焦修正**：默认 1～2 轮有依据的局部修正；没有进展、需要扩大权限或缺少关键来源时停止并说明限制。
6. **决定证据资格**：只有最终通过验证的真实结果，才可以累计为能力、SOP 或宿主经验的成功证据。

最终状态分为：不需要验证、等待验证、已验证、有限完成和失败。它们是当前任务的临时状态，不是新的长期数据库，也不会被塞进启动胶囊。

## 为什么弱模型也能执行

正式协议明确写出容易漂移的主张类型、需要核对的关系、停止条件和结果格式，但不写死某个版本的按钮位置或绝对路径。规划能力较弱而执行可靠的模型可以沿这些语义标准逐项核对；界面或宿主变化后，它仍可根据当前实际状态重新规划。

同一个模型可以用新的检查视角完成复核。换模型、开多个 Agent 或运行自动脚本都只是可选增强，不是 Agent Carry 的必要条件。低风险且边界清楚的验证可以由 Level 1 完成；架构、政策、Schema、安全和高影响冲突继续由 Level 3 决定。

## 对普通用户意味着什么

正常体验仍然是“说出目标，等待结果”。Agent 在内部完成与风险相称的核对：

- 不弹终端，不要求用户跑测试；
- 不为普通聊天生成验收报告；
- 全部通过时只给紧凑结论；
- 发生修正时诚实说明；
- 无法验证时明确告诉用户什么已完成、什么仍未知；
- 不因修正轮次增加学习次数，同一任务最多算一次成功。

完整执行真源是 `core/protocols/RESULT_VALIDATION.md`。资产证据更新继续由 `core/protocols/ASSET_LIFECYCLE.md` 正式拥有；持久写入中断继续使用现有统一触发恢复，不新增后台服务或启动负担。
