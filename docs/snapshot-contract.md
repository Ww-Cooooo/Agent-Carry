# 看板快照说明

看板不直接扫描记忆和能力，也不运行常驻服务。这里有两个必须区分的操作：

1. 网页的“重新读取本地快照”只读取已经存在的 `dashboard/dist/snapshot.js`，不查看正式资产，也不生成文件。网页每 60 秒自动执行一次；手动点击只是立即执行同一次读取。读取请求附加时间戳查询参数且项目不注册 Service Worker，避免浏览器缓存旧文件。快照未变化时不重绘；变化时只热更新数据，不刷新页面、不重建 Three.js、不改变当前栏目、选中项或滚动位置。
2. 正式快照不是可自由编写的 JavaScript。它只能是固定赋值外壳加标准 JSON serializer 生成的 payload；生成与验证都使用精确外壳匹配和 `JSON.parse`，不执行候选文件。来自用户、网页或资产的引号、换行和类似代码的文本必须保持为数据，不能逃逸成额外语句。
3. Agent 动作 `dashboard.refresh-snapshot` 才会根据 `core/schemas/dashboard-snapshot.schema.md` 从正式清单、地图与资产元数据重新生成快照，并原子更新文件。正式资产变化、实例化、模型确认和升级流程必须把这一步作为写侧不变量；用户也可以复制完整动作请求，明确要求 Agent 重建。

Skill 工坊沿用同一只读边界：已安装 Skill 只投影标题、用途、触发、平台和状态，本地导出只投影标题、用途和状态；导出用途必须说明这个 Skill 实际解决什么问题和产生什么结果，不能只重复生成或检查状态。实际入口、来源地址、本机路径、来源资产 ID 和正文不进入快照。旧 Schema 1.1 快照缺少这两个可选列表时按空列表展示。

快照只是展示，不参与 Git 拉取、提交、批准、拒绝、模型切换、升级或隐私导入导出。所有实际动作都通过看板复制完整请求，再由 Agent 路由执行。

为防止看板与助手不一致，快照记录来源摘要和生成时间；生成时先写临时文件并校验，再替换正式快照。只读网页无法扫描来源文件，所以不能自行发现“来源已经变化但快照没变”。它只能根据 `generated_at` 和 `freshness_seconds` 显示保守的“状态可能过期”，这不是来源不一致的证明。来源摘要是否匹配，由执行正式资产变更的 Agent 或显式 `dashboard.refresh-snapshot` 动作检查。

来源摘要不是任意字符串。按 `core/schemas/dashboard-snapshot.schema.md` 的确定性口径，对 `assistant.toml` 和 `instance/` 下除 `README.md` 外的普通文件做“路径 + 文件字节摘要”的二次 SHA-256。这样 Windows、macOS、Linux 或不同宿主只要面对相同正式字节，就会得到同一结果；普通启动不运行这项计算。

快照还带一个极小 `meta.identity_ref`，让本地入口、浏览器地址和实际加载的快照可以互相核对。模板使用 `template`，在线演示使用 `public-demo`，正式实例使用 `ac-` 加实例 ID 的 SHA-256 前 12 位；地址只出现 `ac_kind`、匿名 `ac_ref` 和产品版本，不写助手名称、领域、路径、个人资料或秘密。浏览器标签仍会用正常文字显示“助手名称 · Agent Carry”“尚未创建助手 · Agent Carry”或“在线演示 · Agent Carry”，方便同时打开多个实例时辨认。

入口胶囊只是错入口保护，不是授权令牌。入口没有胶囊时，根 `dashboard.html` 会从已经加载的本地快照补齐；模板正式变成实例、同一实例升级版本时会更新地址。一个已经建立身份的实例入口若加载到另一实例、模板或演示快照，页面会醒目说明不一致并暂停所有“复制执行指令”，但仍允许查看、切换栏目和重新读取本地数据。用户让 Agent 核对安装目录、实例清单和快照并重建入口后，再恢复复制。旧实例缺失 `identity_ref` 时暂按 `legacy-instance` 兼容，下一次正式重建必须补齐匿名稳定编号。

快照生成分为两种明确用途。首次实例化、恢复、模板升级、正式发布审计和用户明确要求的完整维护使用 `strict`：任一正式来源损坏或闭包不一致都保留旧快照，并在当前对话报告缺失项或冲突。日常学习保存、候选晋升和跨会话信号积累使用 `operational`：当前动作正在修改的目标、实例身份、核心清单、地图和不可唯一修复的关键派生索引仍然失败关闭；只有与当前动作无关、可单独定位的待办、治理、延期或 Skill 等展示项可以原样保留并暂不投影。此时新快照必须带有界 `health` 告警，明确隔离数量、受影响类别、源文件未改动和建议的局部修复入口，其他有效内容和普通任务继续可用。两种模式的 `source_digest` 都覆盖全部原始来源字节；隔离不是从摘要中删除文件，也不能把损坏项当成空值。网页仍只读取快照，不会自行修复来源。

实例化、恢复和模板升级还有一个固定顺序：先完成正式内容合并，再从合并后的真实实例重建快照，最后把同一份字节写入 `dashboard/public/snapshot.js` 与 `dashboard/dist/snapshot.js` 并从稳定入口验收。新模板自带的空态快照不能成为实例升级后的最终结果；看板显示模板空态、旧名称、错误版本、错误资产数或两份快照不一致时，升级不能宣布成功。来源没有变化时第二次重建应报告无需更新，不能只为了刷新时间继续改文件。

本地入口验收使用组合证据：系统回读的入口目标、工作目录和参数，根入口与离线资源，快照匿名身份与页面标题，浏览器没有文件缺失／错误页，以及与本次动作相关的结果测试。控制工具能够读取精确地址栏时再核对最终 `dashboard/dist/index.html`；读不到地址栏本身只表示少一项增强证据，不能在其他独立证据一致时单独推翻一个有效实例。真正的入口缺失、目标错误、错误页或身份不一致仍必须停止并修复或回滚。

所有资产卡片都必须从真实存在、类型一致的正式资产正文中投影“标题 + 明确说明”。固定流程（SOP）、能力、记忆、经验、改进建议、普通待办和长期治理不得只显示名称或状态；长期治理还要投影用途、周期和本轮步骤。初始任务族、规划路线、聊天候选和只有地图条目而没有正式资产正文的目标，都不是看板资产，不能进入资产数组或计数。生成前逐项确认来源文件存在、稳定 ID 和 `kind` 与目标数组一致，并确认各资产数组长度与 `assets` 计数一致。`strict` 下任一目标缺失、类型不符或数量对不上都保留旧快照并报告冲突；`operational` 只允许隔离与当前动作无关且拥有独立来源边界的单项，当前目标和正式地图闭包不能被省略。前端不得按已知 ID 维护另一份说明文案，也不得在字段缺失时写入半成品。

从 Dashboard Snapshot Schema 1.1 开始，每条学习建议还要投影低敏的来源说明、建议去向和下一步。来源说明来自正式候选的来源引用类别与有界证据计数，只写“来自哪类真实任务、用户反馈或宿主观察”，不复制事件 ID、路径、原始对话、日志或隐私；来源无法确定时如实显示待补充。建议去向只是当前判断，不表示已经生成记忆、能力、经验或 SOP。旧 1.0 快照仍可读取，下一次正常重建时再渐进补齐。

新生成的普通记忆、习惯、SOP、能力和经验都投影 `status`、`approval_state`、`activation_basis` 与 `risk_tier`；旧快照缺失时可以显示，但界面必须失败关闭执行和自动沿用。记忆还可增加 `subtype`、`scope_summary`、`source_summary` 和少量 `triggers`。`subtype=habit` 只让前端把正式记忆分组显示为“我的习惯”，不会新建一种资产或增加第二份计数；范围与来源必须是低敏、面向用户的摘要。`status=active` 只有授权组合合法时才显示为可按需沿用；任何 `provisional` 都必须是低风险，习惯还必须证明用户明确授权试用或可验证的既有授权迁移。候选不应投影成正式资产；等待确认、复核、历史、暂停、归档、授权缺失和未知状态都失败关闭。历史习惯仍可作为 memory 记录投影，以便解释、恢复或永久删除，但不参与普通任务自动匹配。旧快照没有 `subtype` 时继续按普通记忆显示，前端不得根据标题猜测习惯类型。

新生成的学习建议投影 `observation_state` 与 `observation_basis`。它们只说明用户是否允许继续观察这条候选，不表示允许正式使用；旧快照或非法组合显示为“授权待核对”，不能参与跨会话累计或风险分级验证／复核排序。

快照的 `profile.guidance_mode` 只投影当前交流方式：`step-by-step`、`balanced`、`direct`，模板为 `unselected`。它用于“当前状态”显示，不是用户能力评分，也不拥有方向锁语义。旧实例缺失该字段时前端按 `balanced` 兼容显示；真正修改仍由 `profile.adjust-guidance-mode` 动作写回实例清单后重建快照，网页不能反向写入。

正式实例的 `profile.display_name` 必须来自当前实例档案。看板在左侧固定身份区和总览开头持续显示它，产品 Logo 仍只表示 Agent Carry 本身；模板只显示“尚未创建助手”。升级和重建快照不能把实例名重置为产品名，也不能用方向 ID、宿主名或模型名替代。

能力和 SOP 的正式成熟度来自 Asset Schema 1.3 与 `instance/validations/index.toml` 中闭合的真实结果。快照继续兼容 `reliability`，并保留“未验证、已实践、可靠、跨宿主验证”等详细证据差异；普通用户界面只显示“待验证、需要复核、可使用”三种状态。需要复核优先；未验证或试用中的内容显示“待验证”；至少经过一次已按结果验证门核对、且能在证据索引中闭合的真实任务成功后才显示“可使用”。用户批准实例方向、预览或资产内容只说明允许相应写入，不能被映射成已经通过验证；只在聊天中说“以后使用”而没有更新正式资产，也不能改变快照。“可使用”不等于所有正式成熟度相同，详情、升级和治理仍以正式资产为准。可选证据摘要只投影有界计数和最近验证时间，不复制任务日志。

普通待办的 `visible=false` 只控制看板展示，不等于删除完成记录。看板的信息架构由正式前端版本统一维护；快照只提供数据，不携带已经失效的布局或面板配置。

看板可以显示长期治理和延期任务的上次／下次时间，但不拥有计时与触发语义。正式时间字段和 `instance/maps/time-trigger-map.toml` 由统一触发协议管理；看板自己的 60 秒重新读取只检查快照是否变化，绝不能被当成 180 天治理或延期任务的后台调度器。
