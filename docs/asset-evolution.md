# 资产学习、能力进化与 SOP 成熟说明

本文面向普通用户、接入宿主和开源贡献者，解释 Agent Carry 怎样在日常工作中逐渐学会用户的做事方式，同时避免每次都弹出确认、把全部记忆塞进上下文，或把偶然推断当成长期事实。

可执行真源是：

- `core/protocols/ASSET_LIFECYCLE.md`：什么时候创建、试用、成熟、复核和清理资产；
- `core/schemas/asset-frontmatter.schema.md`：资产元数据结构；
- `core/maps/trigger-registry.toml`：任务结束、跨会话累计、使用时校验等检查点；
- `core/protocols/HOST_INTEGRATION.md`：宿主怎样回传执行证据和学习信号。

本文解释“为什么”和“整体怎样配合”，不加入普通启动上下文。

## 1. 目标：强学习，轻使用

Agent Carry 要同时做到：

1. 用户换模型、换 Agent、换系统后，长期积累仍能带走；
2. 记忆、能力、SOP 和失败经验会根据真实工作逐渐变好；
3. 用户不需要理解内部文件、计数器、测试框架或 Git 流程；
4. 普通任务没有学习价值时安静结束，不固定追问“要不要记住”；
5. 有价值但低风险的规律可以在重复验证后优先请用户复核，但只有用户明确确认具体内容和范围后才能进入可撤销试用；
6. 身份、隐私、安全、重要偏好和高影响流程始终保留用户判断；
7. 任何一次任务只加载本次需要的小地图、少量资产和必要规则。

用户也不需要主动学习内部分类。平时只要用日常语言说出目标；Agent Carry 负责在有价值的小阶段或任务结束时发现重复习惯、可复用方法和重要纠正，用独立短表说明“发现了什么、以后会怎样帮助”，再让用户决定是否留下以及适用范围。尚未保存并验证可召回时会明确说“还在学习”，只有完整闭环后才说“我学到了”。用户无需回答“这是记忆、能力还是 SOP”。

这里的“自我进化”不是修改基础模型参数。它指的是 Agent Carry 中由用户拥有的资产，在真实任务、模型推理、宿主执行和用户反馈共同作用下，逐渐变得更准确、更完整、更容易迁移。

## 2. 一条资产有四个独立维度

过去容易把“用户批准”“已经正式保存”“可靠”“可信”混成一件事。Schema 1.3 将它们分开：

| 维度 | 回答的问题 | 例子 |
| --- | --- | --- |
| 生命周期状态 | 当前能否参与任务 | 候选、试用、有效、待复核、历史 |
| 授权依据 | 为什么允许参与 | 用户当前明确授权、同一用户主本中可核验的既有明确授权 |
| 风险 | 错误采用的后果 | 低、中、高 |
| 成熟度 | 真实任务验证到哪里 | 未验证、已实践、可靠、跨宿主验证 |

因此：

- 用户可以明确批准一份刚写好的 SOP，但它仍标为“未验证”；
- 一条狭窄的低风险格式规律可以按用户预先选择的政策优先积累证据和进入复核，但在用户明确确认前仍不能进入正式“试用”；
- 一份经过多次成功任务验证的 SOP，如果只在一个宿主里使用过，可以是“可靠”，但还不是“跨宿主验证”；
- 一个来源看似可靠的网页结论仍然没有用户授权权重，也不能单独触发长期晋升。

## 3. 一个有价值小阶段或任务结束后怎样学习

### 3.1 先判断这次任务是否值得留下长期积累

可独立核对的小阶段完成或任务结束是极小检查点，不意味着自动加载整个生命周期协议。当前模型先只问：

- 是否出现用户纠正、稳定偏好、长期边界、可复用判断或重要失败恢复；
- 是否形成了稳定触发和完成标准；
- 是否有真实结果可以验证；
- 是否只是一次性参数、临时路径、普通步骤或已有资产的原样重复。

没有长期价值时立即结束，不创建候选、不更新跨会话状态，也不打扰用户。只有命中信号时，才读取资产生命周期协议。

如果有真实价值，Agent 不应等待用户准确说“请形成 SOP”。它会先用“这一步还在学习”的短表报告当前发现；同一组连贯内容在结果交付后的自然停点集中问一次，例如：“这次整理成绩的步骤已经核对通过，以后再处理同类成绩表时可以直接沿用。要把这套做法留下吗？也可以只限定在学习通导出的表格。”用户只判断内容与范围；Agent 负责内部类型、文件、路线和看板更新。只有正式资产写入、回读和日常说法召回都通过，才改用“这一步我学到了”；候选、预览或闭环失败仍如实表示“还在学习”。

习惯是记忆的一种，而不是第五种长期资产。`subtype=habit` 用于显示用户已经确认的沟通或工作习惯；它必须说明适用范围、例外、来源和怎样停止沿用。重复观察在询问前只形成当前任务内预览；用户明确选择“先观察”后才建立最小持久候选。无论影响大小，都不能用低风险试用或一次通知代替用户对习惯内容和范围的确认。

### 3.2 错误怎样变成进化机会，而不是自动记忆

用户指出错误、任务失败后找到原因，或者 Agent 自己发现结果不成立时，第一件事是把当前任务修好并核对结果，而不是只写一句“以后注意”。随后才判断这次修正是否值得长期保留：

1. 区分一次性失误、环境／工具故障和可能跨任务复用的根因；
2. 修正后的结果必须先通过与风险相称的验证；仍为 `limited` 或 `failed` 时，只保留准确限制，不宣称学会；
3. 真正可复用时，候选写清适用情境、原失败、根因、正确替代、证据、范围和反例；完整聊天、终端输出和临时调试信息不进入长期资产；
4. 用户可以在看板中看见候选，再通过当前宿主 Agent 用自然语言纠正、缩小、撤回或批准；
5. 最终按用途进入经验、记忆、能力或 SOP，而不是把所有错误都叫作“经验”或“流程”。

同一任务内改了几轮仍然只算一个事件。没有未来价值的失误在任务结束后丢弃，因此“从错误中学习”会增强 Agent Carry，而不会让文件越来越臃肿。

### 3.3 再识别是不是同一条学习

新学习先生成极小检索特征：

- 目标资产类型；
- 主题和作用对象；
- 一句话核心主张；
- 适用范围和条件；
- 少量别名；
- 来源与稳定事件 ID。

Agent Carry 先通过根地图和领域地图缩小范围。正式资产路线没有命中、且当前任务确实出现学习价值时，才读取 `instance/evolution/index.toml` 中可重建的低敏候选元数据，返回最多 3 条；只有仍无法判断时，才读取这几条候选的 frontmatter、必要正文和代表性证据。候选索引不进入普通启动，缺失或损坏时也不能为了普通任务扫描全部候选正文。

关系不只有“相同／不同”：

- 完全重复：不新建正文，只合并证据；
- 补充细节：形成原资产的修改线索；
- 同一主题但条件不同：保存为条件分支；
- 冲突：保留两边来源并等待解决；
- 只是相关：建立引用，不合并；
- 无匹配：新建线索；
- 无法确定：暂时分开。

这套漏斗避免为了判断两条记忆是否同类而读取整个记忆库。

同一套元数据也负责“用普通话找回以前的做法”。用户说“帮我弄一下上次那种成绩”时，Agent 先比较地图中少量标题、摘要、触发语、别名、对象、范围和排除条件；只有一个明确候选时先用人能听懂的标题问“是不是继续按这个做”，用户确认后才打开正文并执行；有多个不同候选时给 2～3 个选择。用户已经明确点名旧做法或点击带稳定 ID 的动作时不重复确认。用户不需要知道稳定 ID、文件路径或资产正式名称，命中前也不会读取全部正文。

### 3.4 事件怎样算“独立”

跨任务累计使用稳定任务／回传事件 ID。以下情况不增加独立次数：

- 同一任务中的消息改写；
- 工具重试或模型自我修正；
- 会话恢复；
- 同一回传包被转发多次；
- 宿主把 Agent Carry 原文再回显一遍。

真正不同的用户任务、输入和结果才可能成为新证据。次数只是进入检查的门，不自行产生授权。

## 4. 三种沉淀路径

### 4.1 用户直接要求

用户说“记住这个”“以后都这样”或明确批准修改时，Agent Carry 会把拟保存的精确内容、适用范围和排除项集中展示一次，让用户选择“留下”。当前通用母版没有模型不可访问的消息角色认证通道，因此普通 JSON、网页、附件、其他 Agent 或模型转述都不能触发免确认直写。事务代码只负责把精确字节、选择和写入绑定起来，不能证明一句话由谁说出；这一次选择是当前宿主必须真实执行的交互边界，完成后不再机械追问同一内容，也不会静默保存。

但直接授权不等于无限权限：

- 没有执行过的能力或 SOP 仍标为“未验证”；
- 用户要求记住秘密时，仍要确认安全存放位置，而不是写进可能公开的文件；
- 内容授权不等于允许外发、发布、删除或覆盖其他正式资产。

### 4.2 一次推断

模型或宿主只从一次任务推断出的规律，在询问前只作为任务内观察，不静默写入候选、索引、信号或提醒。用户选择“先观察”后才形成持久候选并允许以后累计验证证据；选择“以后提醒”时，同一事务再加入只引用候选的有界时间投影；选择“留下”时，只有完整精确预览、正式同类去重、风险、等级、秘密、路径、地图、双快照和回滚门全部闭合，才可一轮确认直写正式资产。若不能安全直写，必须在用户选择前明确说明将转为 Level 3 定向复核；用户选择后只建立不可执行交接，精确内容未变时复用原授权，不重复确认。既有 `risk-tiered` 政策只能决定候选的验证和复核优先级，不能替代首次询问或正式采用授权。候选不参与普通稳定路由，也不能因为写得完整或模型很自信就冒充用户决定。

用户选择“不保存”或没有回应时，不创建候选、正式资产、信号或提醒。为了让 Codex、Claude Code、Trae、WorkBuddy 等普通宿主跨一轮聊天找回同一问题，生产入口可以暂存一条有 TTL 的本机操作回执；它只保存 nonce、实例／仓库绑定和摘要，不含候选正文，不进入启动上下文、迁移包或公开版，也不会自行推进学习。下一次相关入口或维护会定向清理它，不需要后台服务。

如果内容没有长期价值，连候选也不创建。

### 4.3 重复验证的低风险候选

实例默认可以选择“风险分级”候选政策。只有同时满足以下条件，低风险候选才会被优先带到用户面前复核：

1. 范围狭窄、容易撤销、不替用户作实质决定；
2. 至少两个独立真实任务成功；
3. 主张、范围和条件稳定；
4. 没有正式冲突或未解决显著失败；
5. 外部内容不是唯一证据；
6. 当次能够告诉用户学到了什么、适用范围、依据和撤销方法。

用户明确允许试用后，至少再有一次独立成功复用，并通常累计三个成功任务、两个不同情境，才可以提出进入正常有效状态和“可靠”成熟度。用户看到的是一句简洁说明，不需要操作内部审批界面；验证记录必须在按需证据索引中闭合。

实例政策只是复核排序依据，不是正式资产授权。宿主必须展示具体内容、适用范围、证据和撤销方式，并让用户选择“采用／限定试用”“继续观察”或“不保存”；没有明确采用选择就保持候选。如果无法把问题交付给用户，就不静默晋升。

### 4.4 哪些永远逐项确认

以下内容不能走低风险优先路径，必须完整说明风险并等待用户决定：

- 身份、关系和个人画像；
- 隐私、秘密和敏感资料；
- 安全规则、权限和外发边界；
- 重要偏好、实例方向和专业判断边界；
- 资金、法律、医疗；
- 公开发布、覆盖正式资产和不可逆删除；
- 错误后果难恢复的 SOP。

风险判断不确定时按高风险处理。用户也可以把实例政策改为 `manual-only`，以后所有学习都逐项确认。

## 5. 能力和 SOP 为什么分成两层

### 5.1 可携带核心

能力或 SOP 的核心必须足够完整，让规划能力较弱但执行可靠的模型也能理解。它至少说明：

- 目的、非目标、触发和排除；
- 需要按需加载的资产；
- 输入、输出、质量和缺失处理；
- 模型、宿主、Agent Carry 和用户各自负责什么；
- 判断步骤、分支和停止条件；
- 开放式宿主能力需求；
- 可自主处理和必须确认的边界；
- 外部内容安全；
- 逐步验证和最终验收；
- 失败、自我修正、降级和回退；
- 面向普通用户的结果；
- 任务后怎样提炼学习。

“完整”不等于写死。核心说明目标、判断和验收，不依赖某个版本的按钮位置、固定绝对路径、产品名称或临时命令。

### 5.2 宿主执行经验

宿主执行经验回答的是：“当前这个宿主，在当前环境里，怎样满足核心需要的能力？”

例如同一份“修改网页并验证视觉结果”SOP：

- 可携带核心要求：读取目标页面、修改限定范围、在真实浏览环境验证、保留外部来源和回退；
- 某个宿主经验可能记录：它能直接访问工作区，并可用浏览器工具截取结果；
- 另一个宿主经验可能记录：它不能读本地文件，需要用户提供任务胶囊和截图，再由另一方落盘。

两个宿主都执行同一核心，只是能力映射不同。宿主经验：

- 通过稳定 ID 引用核心，不复制核心；
- 写明宿主档案、环境范围、验证方法、限制和失效信号；
- 不保存凭据、隐藏提示、设备指纹、私人绝对路径或完整日志；
- 当前环境变化时只在使用它时复核；
- 最高只能是“可靠”，不能冒充“跨宿主可携带核心”。

任务发生时先读核心，再从核心列出的引用中按当前宿主筛选，最多展开一个经验。没有匹配经验时，宿主重新映射能力，不扫描全部宿主记录。

## 6. 证据驱动成熟，而不是企业级发布

能力和 SOP 使用四级成熟度：

| 成熟度 | 含义 |
| --- | --- |
| 未验证 `unvalidated` | 文档已形成，但没有真实成功证据 |
| 已实践 `practiced` | 至少一次真实任务成功 |
| 可靠 `reliable` | 通常至少三个独立成功、两个不同情境、范围稳定且无未解决显著失败 |
| 跨宿主验证 `portable` | 先可靠，再跨两个真实宿主档案或一次实质环境变化，通过语义自适应成功 |

这不是流水线审批。普通低风险流程在日常工作中自然积累证据，不要求用户打开多个终端做大型回归。

每次准备增加成功数前，先用 [任务结果验证说明](result-validation.md) 的小型检查包重新比较原始来源、最终产物和本次验收。只有 `validated` 结果能计成功；`limited`／`failed` 只记录限制、反例或失败。同一事件内经过修正最多计一次，不把修正轮次伪装成多个独立任务。

每项资产只保留总次数、最近验证时间和最多 5 个代表性证据引用。显著失败必须记录并触发复核、缩小范围或降低成熟度，不能为了让指标好看而删除失败。

候选审核所需模型等级和最终资产的执行等级是两件事。生成能力或 SOP 时根据目标流程重新计算 `minimum_level`；清楚、低风险、可验证的流程通常允许 Level 1，重要架构和高影响决定仍由 Level 3 负责。

高影响流程可以根据实际风险要求更多验证，但不会把同样强度强加给所有个人任务。

## 7. 规则不在启动上下文里，为什么仍能触发

Agent Carry 将“检查点”和“完整规则”分开：

1. `BOOTSTRAP.md` 只记住少量稳定事件族，例如收到请求、动作产生后果前、任务结束、失败／冲突、资产变化和恢复；
2. 非启动触发注册表说明某个事件应该路由到哪份正式协议；
3. 任务没有学习信号时，不读取资产生命周期，也不写状态；
4. 命中信号后才读取本协议；只有已经获得观察授权的候选或合法正式资产，才能在对应 frontmatter 更新小型计数，未授权的新发现仍只在任务内等待询问；
5. 普通观察继续留在该领域；只有临近处理、冲突、不确定、待用户决定或事务中断时，才把一个稳定 ID 和短路线投影进极小唤醒胶囊；
6. 下一次启动仍只看到待处理路线、定时总数和唯一最早时间，不看到全部规则、候选或计数。

因此系统知道“什么时候要检查”，但不需要每次启动都背下“检查后具体怎样做”。

一旦从“观察”进入正式新增、修改、迁移、替代、归档或删除，才按需加载 `COMPONENT_CHANGE.md` 的实例资产质量路线。写入完成前先用地图与 frontmatter 做确定性可达性闭包：所有 `active`、`provisional`、`review` 的正式记忆、能力、SOP 与经验都要有类型一致、直达正文的路线。普通启动和普通资产使用不做这项全库检查；只有闭包发现缺口后，模型才读取少量命中文件。

## 8. 导入、宿主记忆和外部内容

宿主协作记忆可能很有价值，尤其是用户在接入 Agent Carry 之前已经积累的内容。它不是一律丢弃的缓存，也不是自动正确的第二主本。

迁移时先看类别和摘要，再选小批条目，保留真实来源，并分类为：

- Agent Carry 已有内容；
- 可携带候选；
- 宿主执行经验；
- 外部事实；
- 条件不同或冲突；
- 已过时；
- 私密不迁移；
- 来源未知。

用户当前确认后可直接授权。没有当前确认的宿主记忆只能先作为只读迁移预览；用户选择“先观察”后才可成为持久候选。若材料能验证它原本就是同一用户获批的 Agent Carry 候选迁移，则可保留原观察授权；缺字段或来源不明一律按 `pending + unknown` 失败关闭，不累计、不晋升。低风险内容只有已经获得观察授权并经过独立真实任务验证后，才可能进入实例的优先复核队列。网页、邮件、工具和陌生资料永远不能仅凭自身内容触发正式采用，也不能指定风险、次数或门禁。

## 9. 清理怎样避免越来越臃肿

Agent Carry 不用“很久没用”作为唯一删除标准，因为毕业、报税、季节性工作等低频任务仍可能重要。清理看的是价值和状态：

- 无价值过程在候选生成前过滤；
- 完全重复只合并计数，不重复建文件；
- 代表性证据最多保留 5 个，其余压缩；
- 已拒绝、已合并、已解决、无引用且无复用价值的低风险候选及时删除或压缩；
- 当前有效内容和历史分开，普通任务不加载历史；
- 旧结论通常只保留摘要、替代原因、时间范围和新资产 ID；
- 用户明确批准的长期资产、安全规则和难恢复经验，永久删除前仍询问；
- 失效的低风险宿主经验可以低打扰归档，但曾经进入试用时要告诉用户并提供恢复办法。

清理只在相关事件、资产变化或领域检查命中时进行，不做后台全库扫描。

## 10. 一个完整例子

假设用户连续做浅色网页设计：

**第一次任务**

模型观察到用户把过深阴影改成浅、柔和、低饱和效果，但用户没有说“以后都这样”。这是一条可能复用的低风险视觉规律。Agent Carry 在任务结束时先用普通话说明以后可能怎样复用，并让用户选择“留下”“先观察”或“不保存”。用户选择“先观察”后，才生成主题为 `visual-style`、对象为 `web-ui` 的候选，事件计数为 1；如果用户不保存或没有回应，则不写候选。候选不进入普通稳定路由。

**第二次独立任务**

另一个页面再次出现同样偏好，并由实际截图和用户接受结果验证。Agent Carry 先用主题、对象、主张、范围和条件匹配到原候选，不读取全部记忆。独立事件计数变为 2。若没有冲突、范围确实只是低风险视觉表现，实例又启用了风险分级政策，它会优先请用户决定是否进入 `provisional`，并告诉用户：

> 两次独立页面调整都支持“浅色网页优先使用柔和、低饱和阴影”。你要把它作为可撤销的试用偏好吗？它只用于非品牌强约束的浅色界面；也可以继续观察或这次不保存。

**第三次独立复用**

用户明确选择试用后，新任务命中该偏好，结果再次成功，且出现了不同页面情境。它可以提出转为 `active`；如果验证索引中的记录达到成熟条件，则相关能力可从 `practiced` 提升为 `reliable`。Agent Carry 用普通语言完成确认，不要求用户操作内部审批。

**换到新宿主**

可携带核心仍写“根据目标风格、可访问性和真实截图验证阴影”，不包含旧宿主命令。新宿主没有匹配经验时，根据当前能力重新规划。成功后生成一条新的 `host-execution` 经验，记录它如何取得截图和验证结果。核心在两个宿主中都通过语义自适应后，才可能获得 `portable` 成熟度。

**如果内容换成隐私或秘密规则**

例如模型多次推断“某类健康资料连当前执行模型也不能读取”，重复次数本身不能把它自动升级为新的隐私模式；是否从“当前模型可按任务需要处理最小隐私”改成更严格模式，必须由用户明确确认。反过来，任务确实需要的普通隐私也不会仅因“隐私”二字被错误阻断。API 密钥、密码、令牌、Cookie、私钥、恢复码和登录态则不是可由计数放宽的普通隐私：任何模型都不得读取，认证始终由宿主秘密机制完成。

## 11. 维护者检查表

修改资产学习体系时至少检查：

1. 是否同时更新生命周期协议和 Asset Schema；
2. 是否把新条件登记进统一触发注册表，而不是扩写启动文件；
3. 是否保留来源，阻止外部内容洗白；
4. 是否让能力／SOP 与宿主执行经验保持单向引用和职责分离；
5. 是否更新实例目录说明、接入回传字段和看板快照兼容投影；
6. 是否为旧 Schema 提供保守读取，不强迫全库迁移；
7. 是否只做与风险相称的场景验证；
8. 是否避免把个人实例内容、日志、临时任务包或维护者私密流程写进公开文档。
9. 是否允许用户用不精确的日常语言召回资产，并在任务自然停点主动发现值得沉淀的习惯或方法。
10. 是否让看板把习惯作为记忆子集展示、纠正和停止沿用，而没有重复计数或泄露来源正文。
11. 成功证据是否先通过结果验证门，同一事件修正是否只计一次；
12. `minimum_level` 是否按目标资产重新判断，而非从候选审核等级机械继承；
13. 正式持久变更是否命中修改质量原则，证明根因、数据保留、路线可达、回退和风险对应验证，同时没有把内部维护负担转给用户。
